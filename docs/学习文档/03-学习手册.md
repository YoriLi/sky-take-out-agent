### 代码阅读原则

第一，**先分层、再业务**。在动手看任何一个具体功能之前，必须先明确该文件属于表现层（Controller）、业务层（Service）、持久层（Mapper）还是数据对象层（Entity/DTO/VO）中的哪一层，因为苍穹外卖项目严格遵循分层架构，读错层次会导致把持久层的字段映射逻辑和业务层的规则校验逻辑混为一谈，进而误判代码职责。

第二，**先接口、再实现**。Service、Mapper 均采用接口与实现类分离的写法，阅读顺序永远是先看接口方法签名（方法名、参数、返回值即已经表达了业务意图），再看实现类的具体代码，这样可以先建立"这个方法要做什么"的预期，再验证"它是怎么做的"，效率远高于直接扎进实现细节。

第三，**带着问题读，而不是通读**。本手册每个学时末尾提供检查点问题，请先浏览检查点，明确本学时要解决哪些具体问题，再去读代码，读完立刻用自己的话回答检查点，答不出来就说明该文件没有读透，需要回头重读，而不是不假思索地进入下一学时。

第四，**重复 CRUD 一次读透、后续同类略读**。项目中 Category、Setmeal、SetmealDish 等模块与 Dish、Employee 在代码结构上高度相似（同样是 DTO 接收、Service 编排、Mapper 落库的三层流水线），本手册在学时 5、6 中会指出哪些文件应当"精读"（第一次建立心智模型）、哪些应当"略读"（只看方法签名确认结构一致即可），请严格按此分配阅读精力，避免在结构重复的代码上浪费时间。

第五，**善用全局检索定位调用链**。IDE 或命令行的全文检索（例如 `grep -rn "方法名"`）是理解一个方法在何处被谁调用的关键手段。在学时 3（拦截器）、学时 4（`@AutoFill`）、学时 16（`@Tool`）中会明确要求你用检索工具确认某个注解、某个方法在项目中的完整调用范围，而不是仅凭猜测。

第六，**区分"读懂逐行代码"和"读懂设计意图"**。逐行读懂 Java 语法只是及格线，本手册更看重你能否说出"这段代码为什么要这样设计、如果不这样设计会有什么问题"，例如金额为什么要服务端重算而不是信任前端、为什么要有二次确认机制。第八节"安全加固回顾"和每学时的检查点会反复训练这种设计层面的理解。

第七，**每学时结束前必须完成动手练习**。本手册每个学时都配有一到两个动手练习，这些练习并非可选的附加内容，而是巩固阅读效果的必要环节。人脑对"看懂"和"用得出来"之间存在明显的记忆鸿沟，只有通过亲自修改代码、执行命令、绘制图表这类主动输出行为，才能把被动阅读获得的印象转化为可长期保留、可在面试中随时调用的知识。如果 20 学时的时间压力导致必须在"多读一个文件"和"完成一次动手练习"之间取舍，本手册建议优先保证动手练习的完成度。

第八，**保持"数据库表结构"和"实体类字段"的双向映射习惯**。本项目一共涉及 11 张核心数据表，几乎每一学时都会接触其中一张或多张表对应的 Entity 类。建议在学习学时 1 至学时 11 期间，随身维护一份手绘或电子版的 ER 图草稿，每当在某个学时读到一个新的 Entity 类，就把它的字段和外键关系补充到这张草稿图上。到学时 20 综合串讲时，这张逐步完善的草稿图会自然演变成一张完整、准确、由自己亲手画出而非照抄文档的数据库关系图，这比直接背诵技术文档第三章的 ER 关系摘要要扎实得多。

## 学时 1：项目全景与构建环境（2h）

### 目标

建立对项目整体结构的空间感——三个 Maven 模块各自负责什么、依赖关系如何流动、Spring Boot 应用如何被启动、核心配置项在哪里生效。完成本学时后，你应当能够在不打开 IDE 项目视图的情况下，仅凭包名判断一个类大致应该出现在哪个模块中。

### 阅读文件清单

1. `/workspace/sky-take-out/pom.xml`——父工程 POM。重点看 `<modules>` 标签下声明的三个子模块顺序（`sky-common`、`sky-pojo`、`sky-server`），以及 `<dependencyManagement>` 中统一管理的版本号（Spring Boot 2.7.3、MyBatis、Druid、LangChain4j 等），理解父 POM 的作用是"统一版本、避免子模块各自声明版本号导致冲突"。
2. `/workspace/sky-take-out/sky-common/pom.xml`——基础设施模块 POM。关注其 `<dependencies>` 列表，会发现只有 Lombok、Jackson、JJWT、Aliyun OSS SDK 等工具类依赖，**没有** Web 或 MyBatis 依赖，验证技术文档中"sky-common 不含业务逻辑、被其他模块依赖"的说法。
3. `/workspace/sky-take-out/sky-pojo/pom.xml`——数据对象模块 POM。关注其依赖同样极度轻量（仅 Lombok、Swagger Annotations、Spring Context），没有引入任何 Web 或持久层依赖，理解为什么这个模块要保持"轻依赖"——它会被 sky-server 依赖用于承载请求参数和返回结果，过重的依赖会造成不必要的类路径污染。
4. `/workspace/sky-take-out/sky-server/pom.xml`——主服务模块 POM。这是三个 POM 中最长的一个，逐行核对每一个 `<dependency>`，在纸上或笔记软件里为每个依赖写一句话（解决什么问题），这一步是建立"技术选型—业务需求"映射关系的关键练习。同时注意该模块通过 `<dependency>` 引用了 `sky-common` 和 `sky-pojo`，验证模块间的依赖方向（`sky-server` 依赖前两者，反过来不成立）。
5. `/workspace/sky-take-out/sky-server/src/main/resources/application.yml`——唯一的应用配置文件。分段阅读：`server.port` 确定服务端口；`spring.datasource` 部分理解 Druid 连接池配置及 `${ENV_VAR:default}` 语法（环境变量优先、无环境变量时回退默认值）；`mybatis.configuration.map-underscore-to-camel-case: true` 是数据库下划线字段到 Java 驼峰属性自动映射的开关，务必理解它的作用，否则学时 4 阅读 Mapper XML 时会对字段名不一致产生困惑；`sky.jwt`、`sky.alioss`、`sky.wechat`、`sky.baidu`、`sky.agent` 等自定义配置前缀，分别对应后续学时会讲到的属性绑定类。
6. `/workspace/sky-take-out/sky-server/src/main/java/com/sky/SkyApplication.java`——Spring Boot 启动类。关注类上的注解组合：`@SpringBootApplication` 开启自动配置和组件扫描，`@EnableTransactionManagement` 开启事务管理（为学时 6、8 中大量出现的 `@Transactional` 打下基础），`@EnableCaching` 开启缓存注解支持（为学时 6、11 的 `@Cacheable` 打下基础），`@Slf4j` 提供日志能力。理解这个类虽然代码量极少，但每一个注解都在为后续学时的技术点"开闸放水"。

### 动手练习

在本地（或阅读代码后在纸面上）画出三个模块的依赖箭头图：`sky-server → sky-pojo`、`sky-server → sky-common`、`sky-pojo` 与 `sky-common` 之间是否存在依赖（提示：核对 `sky-pojo/pom.xml` 是否引用了 `sky-common`）。执行 `mvn -pl sky-server -am compile` 尝试单独编译 sky-server 模块并观察 Maven 输出中模块编译的顺序，验证依赖传递关系与你画出的箭头图是否一致。

### 检查点

- 三个模块分别打包成什么产物（JAR）？哪个模块是可独立运行的 Spring Boot 应用？
- 为什么 `sky-pojo` 不能反过来依赖 `sky-server`？如果这样设计会带来什么问题？
- `application.yml` 中 `${SKY_JWT_ADMIN_SECRET:xxx}` 这种写法在没有设置环境变量时会取什么值？在生产环境部署时应该如何设置？
- `map-underscore-to-camel-case: true` 具体解决了什么问题？如果关闭这个配置，`create_time` 字段会映射到 Java 对象的哪个属性（还是完全映射失败）？
- `@EnableCaching` 和 `@EnableTransactionManagement` 分别是为哪些后续学时的注解铺路的？

## 学时 2：统一响应、异常体系与常量（1.5h）

### 目标

理解 Spring Boot 项目中"统一返回结构"和"统一异常处理"这两个工程化设计模式的必要性与实现方式，为后续所有学时打下阅读 Controller/Service 代码的语言基础——本手册后续每一次提到"返回 Result.success"或"抛出业务异常"，都要求你能立刻在脑中还原出完整的执行路径。

### 阅读文件清单

1. `/workspace/sky-take-out/sky-common/src/main/java/com/sky/result/Result.java`——统一响应结构。关注其字段设计：`code`（业务状态码，1 表示成功，0 表示失败）、`msg`（提示信息）、`data`（泛型 `T`，承载具体业务数据）。关注三个静态工厂方法 `success()`、`success(T object)`、`error(String msg)`，理解为什么用静态方法而不是让 Controller 直接 `new Result()`——统一入口便于以后修改返回格式而不影响所有调用点。
2. `/workspace/sky-take-out/sky-common/src/main/java/com/sky/result/PageResult.java`——分页响应结构。只有两个字段：`total`（总记录数）、`records`（当前页数据列表），配合 Lombok 的 `@AllArgsConstructor` 生成的构造方法在 Service 层中被大量调用（学时 5、6、9 中会反复遇到）。
3. `/workspace/sky-take-out/sky-common/src/main/java/com/sky/exception/BaseException.java`——自定义异常基类，继承自 `RuntimeException`。理解为什么继承 `RuntimeException` 而非 `Exception`——运行时异常无需在方法签名上用 `throws` 声明，调用链上不必逐层传递，也不会强迫每个方法都写 `try-catch`。
4. `/workspace/sky-take-out/sky-common/src/main/java/com/sky/exception/AccountLockedException.java`、`AccountNotFoundException.java`、`AddressBookBusinessException.java`、`DeletionNotAllowedException.java`、`LoginFailedException.java`、`OrderBusinessException.java`、`PasswordEditFailedException.java`、`PasswordErrorException.java`、`SetmealEnableFailedException.java`、`ShoppingCartBusinessException.java`——共 10 个业务异常子类，每个都只有几行代码（继承 `BaseException` 并提供构造方法透传消息）。阅读时不要逐个精读，而是快速扫一遍类名和所在业务域，建立"哪个业务模块对应哪个异常类"的索引表，例如登录失败用 `LoginFailedException`、账号被禁用用 `AccountLockedException`、订单相关的所有业务异常统一用 `OrderBusinessException`（并通过消息内容区分具体原因，而非为每种订单错误单独建类）。这里能看出一个设计取舍：细粒度异常类（如密码错误单独一个类）与粗粒度异常类（如订单相关错误全部共用一个类、靠消息文本区分）在本项目中同时存在，值得思考两种做法各自的优劣。
5. `/workspace/sky-take-out/sky-common/src/main/java/com/sky/constant/MessageConstant.java`——错误提示信息常量类。理解常量类的作用：把散落在各处的中文提示字符串集中管理，避免同一个错误提示在不同地方出现不同的措辞（例如"密码错误"和"密码不正确"）。
6. `/workspace/sky-take-out/sky-common/src/main/java/com/sky/constant/StatusConstant.java`——状态常量（启用/禁用），`AutoFillConstant.java`——公共字段方法名常量（配合学时 4 的 AOP 反射调用），`JwtClaimsConstant.java`——JWT Claims 键名常量，`PasswordConstant.java`——密码相关常量（默认密码等）。这四个常量类体量都很小，快速通读即可。
7. `/workspace/sky-take-out/sky-server/src/main/java/com/sky/handler/GlobalExceptionHandler.java`——全局异常处理器，是本学时的重点文件。逐行阅读三个 `@ExceptionHandler` 方法：处理 `BaseException` 的方法直接把异常消息包装成 `Result.error()`；处理 `SQLIntegrityConstraintViolationException` 的方法通过判断异常消息是否包含 `"Duplicate entry"` 关键字来给出友好提示；兜底处理 `Exception` 的方法返回通用错误信息并记录完整堆栈日志。请特别注意这三个处理器的**顺序无关性**——Spring 是按异常类型的继承链自动匹配最精确的处理器，不是按代码书写顺序匹配，这是本学时最容易被误解的知识点。

### 动手练习

在 `GlobalExceptionHandler` 中临时增加一行日志打印（或使用调试器打断点），启动项目后故意触发一次 `BaseException`（例如用错误密码登录管理端）和一次唯一约束冲突（例如新增一个用户名已存在的员工），观察日志输出，验证两条不同路径分别命中了哪个 `@ExceptionHandler` 方法。练习结束后移除临时代码。

### 检查点

- `Result.success(T object)` 和 `Result.success()`（无参）分别在什么场景下使用？分页接口应该用哪一个？
- 为什么自定义异常都继承 `RuntimeException` 而不是 `Exception`？如果继承 `Exception` 会给 Service 层的方法签名带来什么负担？
- `OrderBusinessException` 为什么不像 `PasswordErrorException` 那样为每种错误单独建一个异常类？这种设计的好处和坏处分别是什么？
- 如果一个方法同时可能抛出 `BaseException` 的子类和普通的 `NullPointerException`，`GlobalExceptionHandler` 会分别用哪个方法处理？
- `SQLIntegrityConstraintViolationException` 处理器为什么不直接把原始异常消息返回给前端？

## 学时 3：认证鉴权全链路（2h）

### 目标

完整打通"用户输入密码登录"到"后续每次请求都能识别出这是谁"的全部链路，理解 JWT、拦截器、ThreadLocal 三者如何协同工作。这是本项目除 Agent 模块外**技术密度最高**的一个学时，请预留充足时间反复推敲调用顺序。

### 阅读文件清单

1. `/workspace/sky-take-out/sky-common/src/main/java/com/sky/utils/JwtUtil.java`——JWT 工具类。重点方法 `createJWT()`（签发令牌：接收密钥、过期时间、Claims Map，用 `Jwts.builder()` 链式调用生成字符串）和 `parseJWT()`（验签解析：用同一密钥反向解析出 Claims，密钥不匹配或令牌过期会抛出异常）。理解 JWT 三段结构（Header.Payload.Signature）在代码里分别是如何被组装的。
2. `/workspace/sky-take-out/sky-common/src/main/java/com/sky/properties/JwtProperties.java`——JWT 配置属性类，标注 `@ConfigurationProperties(prefix = "sky.jwt")`，与 `application.yml` 中的 `sky.jwt` 节点字段一一对应。注意管理端和用户端分别有独立的 `adminSecretKey`/`userSecretKey`、独立的 `adminTtl`/`userTtl`、独立的请求头名称 `adminTokenName`/`userTokenName`，这解释了为什么两端令牌不能互用。

## 学时 17：Agent 安全——限流、会话隔离、二次确认（1.5h）

### 目标

聚焦 Agent 模块的安全防线设计，理解为什么一个对话式的 AI 功能相比传统表单提交式的功能需要额外设计限流、会话隔离和二次确认机制。本学时与学时 16 联系紧密，建议在学时 16 结束后尽快连续学习。

### 阅读文件清单

1. `/workspace/sky-take-out/sky-server/src/main/java/com/sky/agent/service/AgentRateLimiter.java`——限流器实现，重点理解"固定窗口限流"算法的具体实现方式：以员工 ID 为 key，记录该员工在当前时间窗口（例如每分钟）内已发起的请求次数，超过阈值（默认 20 次）则拒绝新请求。对比固定窗口算法与滑动窗口、令牌桶等其他限流算法的差异（固定窗口实现最简单，但存在窗口边界处理突发流量的问题，例如窗口切换的瞬间理论上可以在很短时间内发出双倍于阈值的请求），理解本项目选择固定窗口算法是出于实现简单和场景匹配（内部管理端员工使用，无需应对恶意大流量攻击）的权衡而非算法最优。
2. `/workspace/sky-take-out/sky-server/src/main/java/com/sky/agent/service/AgentPendingActionStore.java`——待确认动作存储类，本学时的核心文件。重点理解其存储结构：以某种 key（可能包含 empId 和会话标识）映射到一个"待执行动作"对象，该对象至少包含工具名称、参数、一个可延迟执行的动作（闭包或 `Runnable`/`Supplier` 形式）、以及创建时间。重点关注 TTL（120 秒）的过期检查逻辑——过期的待确认动作即使用户之后回复"确认"也不会被执行，而是提示"确认已超时，请重新发起指令"，理解这个超时机制存在的必要性（防止用户很久之前的一次模糊表达被很久之后的一句无关"确认"意外触发）。
3. `/workspace/sky-take-out/sky-server/src/main/java/com/sky/agent/service/AgentChatService.java`（学时 16 已整体阅读过，本学时专门回头精读 `localChat()` 方法，即无 API Key 时的本地关键词匹配路径）——重点理解这条路径与 LLM 路径的本质差异：不依赖大模型理解自然语言意图，而是通过关键词匹配（例如检测到"营业额""流水"等词判断为查询营业额意图）解析用户输入。对于识别为读操作的意图，直接调用对应 Service 方法并通过 `invokeLocalRead()`（一个与 `AbstractSkill.invoke()` 类似但适配本地路径的方法）发送 `tool_call`/`tool_result` 事件；对于识别为写操作的意图（接单、拒单、取消、派送、完成、开关店），调用 `prepareWriteConfirmation()` 方法解析出具体的工具名和参数，将其注册到 `AgentPendingActionStore` 中并向用户返回一句确认追问（例如"确定要将订单 X 标记为已完成吗？请回复确认或取消"），只有当用户下一轮对话回复确认关键词时，才通过 `executePending()` 取出之前注册的动作闭包并真正执行。这一整套"先登记、后确认、再执行"的流程是本项目应对"AI 误解用户意图导致误操作业务数据"这一核心风险的关键设计，务必透彻理解。

### 动手练习

设想一个具体场景："老板对着手机说了一句'今天生意怎么样，别关店了'"，这句话中同时包含一个读操作意图（查询营业额）和一个否定式的写操作意图（不要关店）。分别用 LLM 路径和本地关键词匹配路径思考各自会如何处理这句话，重点分析本地关键词匹配路径面对"别关店"这种否定式表达时，如果只做简单的关键词命中而不理解否定语义，可能会错误触发"关店"这个危险的写操作——这正是二次确认机制存在的根本原因：即使意图解析环节出现误判，最终执行前的确认追问依然给了用户纠正错误的最后机会。

### 检查点

- 固定窗口限流算法相比滑动窗口算法的优势和劣势分别是什么？本项目为什么足以采用相对简单的固定窗口算法？
- `AgentPendingActionStore` 中待确认动作的 TTL 设置为 120 秒的意义是什么？如果设置为 24 小时会有什么潜在风险？
- 本地模式（无 API Key）下的关键词匹配路径为什么对写操作格外谨慎、必须经过二次确认，而对读操作可以直接执行？
- 会话 ID 格式 `emp:{empId}:{sub}` 中，`empId` 部分起到什么隔离作用？如果去掉这部分，只用前端传来的 `sub`（子会话标识）作为 key，会出现什么安全问题？
- 二次确认机制在 LLM 模式和本地模式下分别是如何实现的？两者是否共用同一个 `AgentPendingActionStore`？

4. `/workspace/deploy/nginx/sky-take-out.conf`——Nginx 配置文件，本学时的核心文件。重点阅读以下几类指令块：`server` 块中 `listen` 和 `server_name` 确定监听端口和域名；`location /` 块通常配置为托管前端构建后的静态资源目录（`root` 指令）并配合 `try_files` 处理 Vue 前端路由的 History 模式刷新 404 问题；`location /api/` 块通过 `proxy_pass` 将请求转发到后端 Spring Boot 服务的地址，并通过 Nginx 的 `rewrite` 或 `proxy_pass` 路径拼接规则完成"去除 `/api` 前缀、替换为 `/admin`"的路径改写（这正是学时技术文档 4.1 节和 6.1 节反复提及的、前端请求路径与后端实际路径不一致的关键转换点，本学时请务必在这份 Nginx 配置文件中找到具体实现这一改写行为的那一行或几行指令）；如果存在 `location /ws` 或类似块，理解 WebSocket 协议升级需要额外配置 `proxy_set_header Upgrade` 和 `proxy_set_header Connection "upgrade"` 两个头部，因为默认的 HTTP 反向代理不会自动处理协议升级请求。
5. `/workspace/deploy/run-local.sh`——本地一键启动脚本，通读理解它依次执行了哪些步骤（可能包括编译打包、设置环境变量、启动 Java 进程等），这个脚本是理解"从源码到可运行服务"这一完整链路最直观的可执行文档。
6. `/workspace/project-rjwm-admin-vue-ts/Dockerfile`——前端容器化构建文件，重点理解其是否采用"多阶段构建"（第一阶段用 Node 镜像执行 `npm run build` 产出静态文件，第二阶段用 Nginx 镜像仅拷贝构建产物），这种多阶段构建方式相比单阶段构建的优势是最终镜像体积大幅缩小（不包含 Node.js 运行时和源码，只包含编译后的静态文件和 Nginx）。
