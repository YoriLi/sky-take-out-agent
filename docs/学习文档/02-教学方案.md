# 苍穹外卖（sky-take-out-agent）教学方案

本方案面向已完成数据结构、操作系统、数据库、计算机原理四门基础课程（掌握程度中等，非完全牢固）以及 Java 语言与 Spring 基础的本科学生，以苍穹外卖智能体改造版（sky-take-out-agent）为教学载体，目标是让学生在一个真实、完整、可运行的商业级项目中，系统掌握 Spring Boot 全栈开发能力，并进一步理解基于 LangChain4j 的 Agent 工程化实现。全文分五章：学情分析与教学目标、知识依赖图谱与学习路径、分单元教学设计、面试专题突击、教学评估方案。教师在讲授本方案前应先完整阅读 `/workspace/docs/学习文档/01-项目技术文档.md`，并在讲课过程中随时对照后端源码 `/workspace/sky-take-out` 与前端源码 `/workspace/project-rjwm-admin-vue-ts` 进行验证式教学，做到"讲一句原理，指一处代码"。

# 一、学情分析与教学目标

## 1.1 学生已知技术清单

在正式进入项目教学之前，教师必须清楚学生已经具备哪些知识储备，哪些储备可以直接复用，哪些储备只是"听过但没做过"。下表列出学生在数据结构、操作系统、数据库、计算机原理、Java、Spring 六个知识来源中，与本项目直接相关的知识点，并标注其在本项目中的关联度（高/中/低），关联度越高说明该知识点在项目中被直接、频繁地使用，教师应重点唤醒。

**数据结构相关知识**：

- 数组与顺序表（关联度：高）。分页查询返回的 `List<T>`、购物车列表、订单明细列表本质都是顺序存储结构，学生需要能够解释为什么 `PageHelper` 返回的 `Page<T>` 继承自 `ArrayList`。
- 哈希表（关联度：高）。`BaseContext` 底层的 `ThreadLocalMap`、`HashMap<String, Session> sessionMap`（WebSocket 会话表）、Redis 的键值存储、`AgentPendingActionStore` 内部的待确认动作表，均以哈希表为核心数据结构，学生此前学过哈希冲突、负载因子等理论，但从未见过其在真实工程中的"落地形态"。
- 树与图（关联度：中）。菜品分类与套餐分类是一层浅层树形结构（分类→菜品），配送范围校验中的路线规划本质是图上最短路径问题，但本项目将其外包给百度地图 API，学生只需理解调用方式，无需自己实现图算法。
- 队列（关联度：高）。Agent 模块的有界线程池内部使用 `LinkedBlockingQueue` 作为任务队列，PageHelper 分页、Redis SCAN 游标扫描本质上也是队列/迭代器思想的应用。
- 状态机（关联度：高，虽然数据结构课程通常不会单独讲授状态机，但状态机是有限自动机（DFA）在数据结构与自动机理论中的具体应用）。订单状态机是本项目最重要的业务建模范式，学生此前如果学过编译原理或自动机理论会有天然的迁移优势，若没学过则需要教师专门用一节课补齐"状态-事件-迁移"的思维模型。

**操作系统相关知识**：

- 线程与线程安全（关联度：高）。Tomcat 使用线程池处理 HTTP 请求，线程会被复用，这直接决定了 `ThreadLocal` 必须在请求结束后清理，否则会出现"张三看到李四登录信息"的严重安全事故。学生此前学过进程/线程调度，但很少接触"线程复用导致的状态污染"这一具体陷阱。
- 锁与并发控制（关联度：中）。`AgentRateLimiter` 的限流计数器、Redis 客户端连接池的并发访问、`AgentConfig` 有界线程池内部的任务提交，都涉及并发安全问题，Spring 官方组件已经封装好线程安全实现，学生需要理解"为什么不用自己写锁"。
- 内存管理（关联度：中）。ThreadLocal 内存泄漏本质是"该被回收的对象因为被强引用链持有而无法被垃圾回收"，这与操作系统课程中虚拟内存、垃圾回收的概念有交叉，教师应引导学生用 GC Roots 的视角理解为什么忘记调用 `remove()` 会导致内存膨胀。
- I/O 模型（关联度：中）。SSE 基于 HTTP 长连接的流式响应、WebSocket 基于 TCP 的全双工通信，都涉及阻塞/非阻塞 I/O 的取舍，`SseEmitter` 内部依赖 Servlet 3.0 的异步请求处理机制（`AsyncContext`），这是操作系统 I/O 多路复用理论在 Web 框架层的具体投影。

**数据库相关知识**：

- 关系模型与范式（关联度：高）。11 张核心表的设计、外键关联、`setmeal_dish` 中间表处理套餐与菜品的多对多关系，是数据库课程"ER 模型转关系模型"章节的直接应用。
- 事务与 ACID（关联度：高）。新增菜品含口味、用户下单扣减购物车、支付成功回调更新订单状态，均标注 `@Transactional`，学生需要将课堂上"原子性、一致性"的抽象概念对应到"要么全部插入成功，要么全部回滚"的具体代码行为。
- 索引与查询优化（关联度：中）。订单表按 `user_id`、`status`、时间区间频繁查询，理论上应建立组合索引，教师可以借此项目讲授 EXPLAIN 执行计划分析，是对数据库课程"索引选择性"内容的实战补充。
- SQL 注入与预编译（关联度：高）。MyBatis 的 `#{}` 与 PreparedStatement 直接对应数据库课程中"SQL 注入原理与防御"的内容，学生此前多是理论了解，本项目让其看到真实代码中的防御写法。

**计算机原理相关知识**：

- 编码与序列化（关联度：中）。JWT 的 Base64 编码、Jackson 的 JSON 序列化、AES-GCM 加解密（微信支付回调）都建立在计算机原理中"数据的二进制表示与编码转换"基础上。
- 网络协议分层（关联度：高）。HTTP、WebSocket、TCP 三者的关系，Nginx 反向代理的路径改写，都要求学生对协议栈有基本认知，教师应结合网络原理课程中的"应用层协议基于传输层"讲清楚为什么 WebSocket 需要"协议升级"这一步。

**Java 与 Spring 基础相关知识**：

- 面向对象三大特性、接口与实现分离（关联度：高）。Service 接口与 Impl 分离、Mapper 接口、`AgentAssistant` 接口的动态代理生成，都是"接口编程"思想的直接体现。
- 反射（关联度：高）。`AutoFillAspect` 通过反射调用 `setCreateTime` 等方法，`AiServices` 内部通过反射扫描 `@Tool` 注解方法，学生此前学过反射 API 但很少见过工业级用法。
- 泛型（关联度：中）。`Result<T>`、`PageResult`、`List<OrderVO>` 大量使用泛型封装返回值，教师应强调泛型在"类型安全"与"代码复用"之间的权衡。
- IoC/DI、注解驱动开发（关联度：高，但学生基础通常薄弱，需要重点讲解）。`@Autowired`、`@Service`、`@Component`、`@Configuration` 是本项目几乎每个类都会用到的基础设施，学生即便学过 Spring 基础，也大多停留在"能跑起来"的层面，缺乏对 Bean 生命周期、依赖注入原理的深入理解。

## 1.2 本项目需要掌握的新技术清单

按照"必须掌握""深入理解""了解原理"三级分类，帮助教师把有限课时分配到真正重要的知识点上，避免平均用力。

**必须掌握（要求学生能独立编码实现，笔试/面试可清晰讲述原理并结合本项目回答）**：

- Spring Boot 自动配置机制、分层架构（Controller/Service/Mapper）、统一响应结构 `Result<T>` 与全局异常处理 `@RestControllerAdvice`。
- MyBatis XML 映射、动态 SQL 标签（`<if>`/`<where>`/`<set>`/`<foreach>`）、`#{}` 与 `${}` 的本质区别。
- PageHelper 分页插件的使用方式与基本原理（ThreadLocal 传参 + MyBatis 拦截器改写 SQL）。
- JWT 的组成结构、签发与验签流程、结合 `HandlerInterceptor` 完成鉴权拦截。
- `ThreadLocal` 及其在 `BaseContext` 中的用法，特别是"必须清理"这一工程纪律。
- AOP 核心概念（切点、通知、织入）及其在 `AutoFillAspect` 中自动填充公共字段的具体实现。
- 订单状态机的设计思想与代码实现，能够独立画出状态迁移图并对照 `OrderServiceImpl` 中每个状态转换方法。
- Redis 基本数据类型及 `RedisTemplate` 使用方式，`@Cacheable`/`@CacheEvict` 声明式缓存。
- 文件上传的工程规范（大小限制、扩展名白名单、UUID 重命名防覆盖/防路径穿越）。

**深入理解（要求学生能解释设计动机、能对比替代方案的优劣，但不要求从零手写底层实现）**：

- Spring IoC 容器的 Bean 生命周期、三级缓存解决循环依赖的大致思路（`allow-circular-references: true` 背后发生了什么）。
- WebSocket 与 SSE 的协议差异、适用场景边界，以及本项目"来单提醒用 WebSocket、AI 对话用 SSE"的选型逻辑。
- LangChain4j 的 `AiServices` 声明式编程范式、Function Calling 的完整执行流程、`@Tool`/`@P`/`@SystemMessage`/`@MemoryId` 各注解的职责边界。
- Agent 安全工程实践：限流、会话隔离、二次确认、有界线程池、结果截断，这些不是某一个"知识点"而是一整套系统性防御思路，需要学生具备综合设计能力。
- 微信支付 V3 的签名验签与 AES-GCM 回调解密、幂等性设计。

**了解原理（要求学生知道其存在、大致作用，不要求编码，也不作为考核重点）**：

- Druid 连接池的监控原理与慢 SQL 日志采集机制。
- Apache POI 操作 Excel 模板填充数据的底层 OOXML 文件结构。
- 百度地图 Geocoding 与路线规划 API 的坐标系转换细节。
- Nginx 反向代理的具体配置语法（`proxy_pass`、`pathRewrite`）。

## 1.3 教学目标（知识/能力/素养三维度）

**知识目标**：学生学完本方案后，应能够准确复述 Spring Boot 分层架构的职责边界、MyBatis 动态 SQL 的核心标签用法、JWT 无状态鉴权的完整流程、AOP 切面编程解决横切关注点问题的原理、Redis 声明式缓存的注解语义、WebSocket 与 SSE 的协议级差异，以及 LangChain4j Function Calling 从模型决策到工具执行再到结果回灌的完整闭环。这些知识点均要求"不看代码也能讲清楚原理，看代码能准确指出对应实现"，即达到大学教材"理解并能应用"的认知层级，而非仅仅"知道术语"。

**能力目标**：学生应具备独立阅读中大型 Spring Boot 项目源码的能力，能够沿着一条请求链路（例如"用户下单"）从 Controller 一路追踪到 Mapper 再到数据库，清楚每一层做了什么、为什么这么分层；应具备独立新增一个完整业务模块（Controller+Service+Mapper+Entity+DTO+VO）的编码能力；应具备为现有系统增加一个新的 Agent Skill 工具的能力，包括定义 `@Tool` 方法、处理 String 参数防呆、通过 `invoke()` 模板方法接入事件推送；应具备基本的系统安全意识，能够在设计新接口时主动考虑越权访问、SQL 注入、敏感信息泄露等风险点并给出防御方案。

**素养目标**：通过阅读本项目中大量详尔的中文源码注释（如 `AutoFillAspect`、`AgentChatService` 中逐行讲解式注释），培养学生"写代码不仅是让机器执行，更是让同事和未来的自己能看懂"的工程素养；通过 Agent 安全模块的学习，培养学生在设计任何自动化/智能化系统时"默认不信任外部输入、默认给写操作加二次确认"的审慎态度；通过对比"传统 CRUD 后台"与"AI 老板助手"两种产品形态在同一套 Service 层之上的复用设计，培养学生"好的分层架构应该能够被多种前端形态复用"的架构思维。

# 二、知识依赖图谱与学习路径设计

## 2.1 知识前置依赖图（文本 DAG）

下面用文本形式表示本项目所涉及各技术点之间的前置依赖关系，形成一张有向无环图（DAG）。箭头 `→` 表示"左边是右边的前置知识"，即必须先掌握箭头起点，才能顺利学习箭头终点。教师授课顺序应严格遵循该拓扑序，不可跳跃式讲解后置知识。

```
Java 基础（类/接口/反射/泛型/异常）
        │
        ▼
Spring IoC / DI（Bean 容器、@Component、@Autowired）
        │
        ▼
Spring Boot 自动配置（starter、application.yml、条件化装配）
        │
        ├──────────────────┬───────────────────┐
        ▼                  ▼                   ▼
   MyBatis（Mapper/XML/  AOP（@Aspect/切点/  Servlet 基础
   动态SQL/PageHelper）    通知/AutoFill）    （拦截器/Filter）
        │                  │                   │
        │                  │                   ▼
        │                  │              JWT（签发/验签/无状态鉴权）
        │                  │                   │
        │                  └───────┬───────────┘
        │                          ▼
        │                 拦截器整合鉴权链路
        │                 （Interceptor + ThreadLocal + BaseContext）
        │                          │
        ▼                          ▼
   订单/菜品等业务模块 CRUD  ──────► 完整业务闭环（含事务、状态机）
        │
        ▼
     Redis（缓存/RedisTemplate/@Cacheable）
        │
        ▼
  WebSocket（长连接/来单提醒）
        │
        ▼
  SSE（流式响应/text-event-stream）
        │
        ▼
  LangChain4j（AiServices/@Tool/Function Calling）
        │
        ▼
  Agent Skill 层设计（每请求装配/String防呆/二次确认/限流/线程池隔离）
```

该依赖图揭示了几个教学关键点。第一，Spring IoC/DI 是绝大多数后续技术的地基，学生若对 `@Autowired` 背后的容器机制一知半解，后面学 AOP、学 Agent 每请求装配 Skill 时会持续卡壳，因此单元 1 必须把 IoC 讲透，而不能因为学生"用过 Spring"就一带而过。第二，AOP 与 JWT 拦截器分别走两条独立支线，但都汇聚到"拦截器整合鉴权链路"这一节点，说明 `BaseContext` 是连接两条技术线的关键枢纽，教师应在讲授单元 3 时明确回指单元 1、单元 2 中已经出现过的 `BaseContext` 用法。第三，LangChain4j 处于依赖链的末端，说明 Agent 模块不是一个孤立的新技术，而是建立在扎实的 Spring Boot 工程能力（尤其是 Service 层的可复用性、AOP 代理的透明性）之上的高阶应用，教师必须让学生先吃透传统后台开发能力，才能真正理解"为什么 Skill 不需要是 Spring Bean，却依然能享受到 AOP 增强"这一核心设计决策。

## 2.2 学习路径总纲（由已知到未知）

学习路径按照"学生已知→项目新知→项目深化→系统综合"四个梯度，设计 8 个渐进式教学单元，每个单元建立在前一单元的能力基座上，禁止跳跃。

第一步，从学生已经具备的 Java/Spring 基础出发，进入**单元 1：Spring Boot 分层架构与项目骨架**，通过重新审视 Controller/Service/Mapper 三层职责、Maven 多模块拆分、统一响应结构，把学生原本零散的 Spring 知识组织成一套"能读懂任意 Spring Boot 项目骨架"的系统认知，这一步的核心是"架构感"的建立，而非具体技术点的堆砌。

第二步，进入**单元 2：持久层**，在已经理解分层的基础上，深入 Mapper 层内部，学习 MyBatis 动态 SQL、PageHelper 分页、AOP 自动填充公共字段，这是学生第一次接触"用注解+反射自动完成重复劳动"的编程范式，为后续理解 AOP 拦截器、Spring Cache 声明式缓存打下方法论基础。

第三步，进入**单元 3：认证鉴权**，将 Servlet 拦截器、JWT、ThreadLocal 三项技术整合起来解决"如何知道当前是谁在操作系统"这一贯穿全项目的核心问题，这一单元讲完后，学生应能够独立回答"为什么 Controller 方法里不用传 userId 参数却能拿到当前用户"。

第四步，进入**单元 4：业务逻辑（订单全生命周期与状态机）**，这是全项目最考验综合能力的单元，要求学生综合运用前三个单元的知识（分层、持久层、鉴权）去理解一条完整的业务链路，同时引入状态机、金额重算、支付回调幂等性等新概念，是从"会用技术"到"会设计业务"的关键跃升。

第五步，进入**单元 5：缓存与实时通信**，在业务链路已经打通的基础上补充性能与体验层面的技术——Redis 缓存减少数据库压力，WebSocket 实现实时推送，这一单元强调"锦上添花"而非"生死攸关"，帮助学生建立性能优化的分层意识（先保证正确性，再考虑性能）。

第六步，进入**单元 6：文件上传与第三方集成**，引入与外部系统交互的工程规范（OSS 上传、百度地图、微信 OAuth），这是学生第一次系统学习"如何安全地对接不受自己控制的外部服务"，涵盖签名校验、参数白名单、超时重试等实战话题。

第七步，进入**单元 7：Agent 核心**，学生此时已经具备完整的 Spring Boot 全栈能力，正式进入 LangChain4j 与 SSE 流式对话的学习，理解 Skill 模式如何在不破坏已有 AOP 增强的前提下，把传统后台能力包装成 AI 可调用的工具。

第八步，进入**单元 8：Agent 安全与工程化**，站在系统架构师视角审视整个 Agent 子系统的防御设计，完成从"能跑"到"能上生产"的最后一跃，同时呼应单元 3 到单元 6 中学过的鉴权、限流、越权防护等安全话题，实现知识的螺旋式回归与升华。

# 三、分单元教学设计

## 单元 1：Spring Boot 分层架构与项目骨架

**教学目标**：学生能够准确说出 Controller、Service、Mapper 三层各自的职责边界与调用方向；能够解释 Maven 多模块拆分（sky-common/sky-pojo/sky-server）的设计动机；能够读懂 `application.yml` 中环境变量注入语法并说明其安全意义；能够独立设计一个统一响应结构并将其应用到新接口；能够使用 `@RestControllerAdvice` 编写至少两级异常处理逻辑。

**先修知识**：Java 接口与实现分离、Maven 依赖管理基本概念、Spring `@Component`/`@Autowired` 的初步使用经验（即便使用得不熟练也可以，本单元会重新梳理）。

**核心知识讲解**：

分层架构的本质是"单一职责原则"在系统级别的应用。Controller 层只做三件事：接收 HTTP 请求参数、调用 Service、把结果包装成统一响应格式返回，绝对不允许在 Controller 里写 SQL 或者复杂的业务判断逻辑；Service 层是业务逻辑的唯一合法居所，事务边界（`@Transactional`）也画在这一层；Mapper 层只负责"把 Java 方法调用翻译成 SQL 并执行"，不掺杂任何业务判断。本项目中 `com.sky.controller.admin`、`com.sky.controller.user`、`com.sky.controller.notify`、`com.sky.agent.controller` 四个包印证了"按角色而非按技术划分 Controller"的组织方式，教师应带学生打开 `EmployeeController.java`，逐行核对其方法体是否只有"调用 Service+封装 Result"两步，凡是发现 Controller 里出现 `if/else` 业务判断的，都应当追问"这段逻辑是不是应该下沉到 Service"。

Maven 多模块拆分体现了依赖方向的工程约束。`sky-common` 处于依赖链最底端，只包含无业务含义的基础设施（`Result`、`BaseException`、`JwtUtil` 等），因此不依赖任何其他自定义模块；`sky-pojo` 存放数据对象，同样保持轻量，仅依赖 Lombok/Jackson/Swagger；`sky-server` 是唯一的可执行模块，依赖前两者并实现全部业务。这种拆分方式保证了"底层模块不知道上层模块的存在"，如果学生将来在 `sky-common` 里写了一句 `import com.sky.controller.xxx`，就说明依赖方向反了，这是架构腐化的典型信号，教师应重点强调这一"单向依赖"纪律，并解释这与操作系统课程中"分层设计、下层不感知上层"的思想是同构的。

统一响应结构 `Result<T>` 解决的问题是：前后端约定一套固定的响应外壳（`code` 表示成功/失败，`msg` 携带错误信息，`data` 携带业务数据），前端无需针对每个接口单独判断成功失败逻辑，只需统一检查 `code` 字段。分页场景进一步封装出 `PageResult`（含 `total` 总数和 `records` 当前页数据），被 `Result<PageResult>` 包裹后返回。教师应要求学生阅读 `sky-common` 中 `Result` 类的源码，理解为什么使用静态工厂方法（`Result.success()`、`Result.error()`）而不是直接 `new Result()`——工厂方法可以在内部固定 `code` 取值，避免调用方每次手写魔法数字导致的错误。

全局异常处理体现了"关注点分离"在异常处理领域的应用。本项目 `GlobalExceptionHandler` 设计了三级处理策略：第一级处理业务自定义异常（继承自 `BaseException`），直接把异常信息原样返回给前端，因为这类异常的消息本身就是为用户设计的友好提示；第二级专门捕获数据库唯一约束冲突异常，将其转换为"记录已存在，请勿重复添加"这样的中文提示，避免把 MySQL 原始报错（包含表名、字段值等内部信息）暴露给客户端；第三级是兜底处理，捕获所有未预料的异常，向前端返回统一的"未知错误"，同时在服务端日志中记录完整堆栈，供开发人员排查。这种分级处理是"防御性编程"思想的具体实践，学生应能解释为什么不能让 Controller 层自己写 `try-catch`（会导致每个接口重复相同的异常处理代码，且容易遗漏）。

**代码实操指引**：

要求学生按以下步骤动手实践：第一步，在 IDE 中打开 `sky-take-out` 项目并成功启动，观察启动日志中 Spring Boot 自动配置生效的关键日志行；第二步，选择一个简单模块（如 `category` 分类管理），完整跟踪一次分页查询请求从 `CategoryController.page()` 到 `CategoryServiceImpl.pageQuery()` 再到 `CategoryMapper.xml` 中对应 SQL 的完整调用链，在每一层打上断点观察参数变化；第三步，故意在某个 Service 方法中抛出一个未捕获的 `RuntimeException`，观察 `GlobalExceptionHandler` 兜底处理是如何工作的，并对比抛出 `BaseException` 子类时前端收到的响应差异；第四步，仿照现有模块，独立新增一个极简的"通知公告"CRUD 模块（Entity+DTO+VO+Controller+Service+Mapper），完整走一遍分层开发流程。

**易错点/常见误区**：

学生最常见的错误是把业务判断写进 Controller，理由通常是"反正逻辑简单，写哪层都行"，教师需要反复强调分层不是为了"当前这一次好不好写"，而是为了"未来这段逻辑需不需要被其他入口复用"——本项目的 Agent 模块正是复用了 Service 层而非 Controller 层的最佳证明，如果业务逻辑散落在 Controller 里，Agent 就无法复用。第二个常见误区是把 `sky-pojo` 模块里的 Entity 直接作为接口的返回值，导致密码字段等敏感信息被序列化到前端，正确做法是设计专门的 VO 并显式排除敏感字段。第三个常见误区是异常处理"一把梭"，即所有异常都用一个 `@ExceptionHandler(Exception.class)` 兜底，这会导致所有业务异常都变成"未知错误"提示，用户体验极差，必须按异常继承层级分级处理。

**面试真题**：

1. Spring Boot 项目为什么要分 Controller/Service/Mapper 三层？如果不分层会有什么问题？答案要点：分层是为了单一职责与代码复用，不分层会导致业务逻辑与展示逻辑/持久化逻辑耦合，难以在多个入口（Web/Agent/定时任务）中复用同一段业务逻辑，也难以单独测试某一层。
2. `@RestController` 与 `@Controller` + `@ResponseBody` 有什么区别？答案要点：`@RestController` 是二者的组合注解，语义上表示该类所有方法的返回值都直接作为响应体（通常是 JSON），不经过视图解析器。
3. 项目里为什么要区分 Entity、DTO、VO 三种对象，而不是全部用一个类？答案要点：三者职责不同——Entity 对应数据库表结构，DTO 是请求参数（只含必要字段，且不信任客户端传入敏感字段如 userId），VO 是响应视图（按展示需要裁剪或聚合，屏蔽敏感字段），混用会导致安全漏洞（敏感字段泄露）和耦合度过高（表结构变化直接影响接口契约）。
4. 全局异常处理器如何决定用哪个 `@ExceptionHandler` 方法处理某个异常？答案要点：Spring 按异常的继承链，从最精确匹配的类型开始查找，找到最具体的处理器进行处理，因此设计异常类体系时应遵循"具体异常继承自抽象异常"的层次结构。
5. Maven 多模块项目中，为什么 `sky-common` 不能依赖 `sky-server`？答案要点：这会造成循环依赖（`sky-server` 本身依赖 `sky-common`），并且违反了"底层基础设施模块不应感知上层业务实现"的架构原则，一旦破坏这个方向，模块边界形同虚设。

**本单元产出**：学生独立完成一个包含 Controller/Service/Mapper 三层、Entity/DTO/VO 三类对象、统一响应封装、基础异常处理的最小 CRUD 模块代码，并能够在课堂上现场讲解该模块的调用链路。

## 单元 2：持久层（MyBatis + PageHelper + Druid）

**教学目标**：学生能够独立编写包含动态 SQL 标签的 MyBatis XML 映射文件；能够准确说明 `#{}` 与 `${}` 的本质区别及安全含义；能够解释 PageHelper 分页插件的工作原理并正确使用；能够独立实现一个自定义注解 + AOP 切面来完成横切逻辑（以 `AutoFillAspect` 为原型）。

**先修知识**：SQL 基础（SELECT/INSERT/UPDATE/DELETE、JOIN、GROUP BY）、Java 注解基本语法、单元 1 中建立的分层架构认知。

**核心知识讲解**：

MyBatis 动态 SQL 解决的核心问题是"同一个查询接口需要支持多种可选过滤条件的组合"。以本项目 `OrderMapper.xml` 中的 `pageQuery` 为例，管理端订单列表可能按订单号过滤、按手机号过滤、按状态过滤、按时间区间过滤，这些条件任意组合都要合法，如果为每种组合手写一条 SQL，组合数会呈指数级增长，因此 MyBatis 提供 `<where>` 标签包裹若干 `<if test="条件">`，仅当参数非空时才拼接对应的 SQL 片段，且 `<where>` 会自动处理开头多余的 AND 关键字。`<set>` 标签用于 UPDATE 语句的类似场景，例如 `EmployeeMapper.xml` 中的更新操作只想更新非空字段，`<set>` 自动去除末尾多余的逗号。`<foreach>` 标签用于集合遍历，典型场景是批量插入订单明细（`orderDetailMapper.insertBatch()`）或者构造 IN 查询。教师应带学生对照打开 `DishMapper.xml`，逐行分析其分页查询是如何通过 LEFT JOIN 关联分类表、又是如何通过多个 `<if>` 实现按名称/分类/状态灵活过滤的。

`#{}` 与 `${}` 的区别是本单元最重要的安全知识点。`#{}` 在底层会被编译为 JDBC 的 `PreparedStatement` 占位符 `?`，参数值通过 `setXxx()` 方法单独传入数据库驱动，数据库会将其视为纯数据而非 SQL 代码的一部分，因此天然免疫 SQL 注入；而 `${}` 是纯字符串拼接，如果拼接的内容来自用户输入且未经校验，攻击者可以构造出 `' OR '1'='1` 之类的恶意片段改变原始 SQL 的语义。本项目全部业务查询均使用 `#{}` 参数绑定，教师应在课堂上现场演示：如果把某个查询的 `#{status}` 替换成 `${status}`，构造恶意输入会导致什么后果，用真实攻击场景让学生对这一知识点形成肌肉记忆，而不是死记硬背"`${}` 不安全"这句结论。

PageHelper 的分页原理建立在 MyBatis 拦截器机制之上。调用 `PageHelper.startPage(pageNum, pageSize)` 时，分页参数会被存入一个 `ThreadLocal` 变量；紧接着执行的下一条 MyBatis 查询在真正发往数据库之前，会经过 PageHelper 注册的 `Interceptor`，该拦截器从 ThreadLocal 中取出分页参数，先执行一次 `SELECT COUNT(*)` 得到总记录数，再对原始 SQL 追加 `LIMIT offset, pageSize` 只取当前页数据，最终把总数和当前页数据一起封装进 `Page<T>` 对象中返回；查询完成后 ThreadLocal 被自动清空。教师需要特别强调一个容易被忽视的使用纪律：`startPage()` 与紧随其后的查询之间不能插入任何其他 MyBatis 查询，否则分页参数会被"用错对象"，这是初学者最常踩的坑。本项目 `EmployeeServiceImpl.pageQuery()` 是标准范例，`PageHelper.startPage()` 后立即调用 `employeeMapper.pageQuery(dto)`，中间不夹杂任何其他数据库操作。

AOP 自动填充是本单元与单元 1 分层思想的进一层深化——如果不用 AOP，每个新增/修改方法都要手写四行"设置创建时间、创建人、更新时间、更新人"的重复代码，AOP 把这段横切逻辑集中到一个切面类里统一处理。本项目 `AutoFillAspect` 的实现细节值得逐行精讲：切点表达式 `execution(* com.sky.mapper.*.*(..)) && @annotation(com.sky.annotation.AutoFill)` 由两部分组成，前半部分限定拦截范围是 `com.sky.mapper` 包下的所有方法，后半部分进一步限定只拦截标注了自定义注解 `@AutoFill` 的方法，两者用 `&&` 组合缺一不可——如果只有前半部分，会拦截 Mapper 层所有方法（包括不需要自动填充的查询方法），如果只有后半部分，注解可能标注在任何类的方法上都会被拦截，范围过大。`@Before` 前置通知在目标方法执行前运行，通过 `JoinPoint` 获取方法签名与实际传入参数，通过反射读取 `@AutoFill` 注解的 `value()` 得到操作类型（INSERT 或 UPDATE），再通过反射调用实体对象的 `setCreateTime`/`setCreateUser`/`setUpdateTime`/`setUpdateUser` 方法完成字段填充。教师应引导学生思考：为什么这里必须用反射而不是直接 `((Employee) entity).setCreateTime(now)` 这样的强类型调用？因为切点覆盖了整个 `com.sky.mapper` 包，方法参数可能是 `Employee`、`Dish`、`Category` 等任意实体类型，切面代码在编写时无法预知具体类型，只能通过反射在运行时动态调用同名方法，这正是 AOP"通用性"与"类型安全"之间必然的权衡取舍。

**代码实操指引**：

要求学生完成以下实操：第一步，打开 `OrderMapper.xml` 找到 `pageQuery` 语句，手工画出当四个过滤条件全部为空、全部非空、部分非空三种情况下，`<where>` 标签最终会拼接出的完整 SQL 文本；第二步，故意将某条查询语句中的一个 `#{}` 改写为 `${}`，通过 Postman 构造恶意参数验证 SQL 注入是否成功（在本地测试环境，禁止对生产库做此类实验）；第三步，在自己单元 1 中新增的模块上补充分页查询接口，正确使用 `PageHelper.startPage()`；第四步，仿照 `AutoFillAspect` 的实现方式，独立设计一个新的自定义注解（例如 `@LogOperation`）与对应切面，在方法执行前后打印操作日志，体会"横切关注点"的抽取过程。

**易错点/常见误区**：

学生常犯的错误之一是在 `<if test="status != null">` 中忘记同时处理"空字符串"的情况，导致前端传入空字符串 `""` 时条件仍然成立但拼出无意义的 SQL 片段，正确写法应结合 `!= null and status != ''`。错误之二是滥用 `${}` 图省事，例如动态排序字段（`ORDER BY ${sortField}`）确实是 `${}` 的合理使用场景之一（因为列名无法用占位符参数化），但学生容易把这个"合理例外"误用到本可以用 `#{}` 的普通参数上，教师应明确划出"`${}` 仅限动态表名/列名/排序方向等结构性拼接，其余一律 `#{}`"这条纪律。错误之三是自定义 AOP 切面时，切点表达式写得过于宽泛（比如漏写注解限定条件），导致意外拦截到不该被处理的方法，产生难以定位的 Bug。

**面试真题**：

1. `#{}` 和 `${}` 的区别是什么？请结合本项目说明为什么全部使用 `#{}`。答案要点：`#{}` 编译为预编译占位符防注入，`${}` 是字符串拼接存在注入风险；本项目所有面向用户输入的参数都用 `#{}`，因为不存在需要拼接列名/表名等结构性内容的场景。
2. PageHelper 为什么要求紧跟在 `startPage()` 之后立即执行查询？答案要点：分页参数存放在 ThreadLocal 中，只会被"下一条"执行的 SQL 消费，中间插入其他查询会导致分页参数被错误应用或提前消耗。
3. Spring AOP 底层是如何实现方法拦截的？答案要点：默认基于动态代理，目标类实现了接口时使用 JDK 动态代理，否则使用 CGLIB 生成子类代理，在代理方法中织入前置/后置/环绕逻辑后再调用真实方法。
4. 为什么 `AutoFillAspect` 的切点表达式要同时限定包路径和注解，而不能只用其中一个？答案要点：只限定包路径会拦截该包下所有方法（包括查询方法，造成不必要的性能开销和错误行为），只限定注解则可能拦截到其他包中偶然使用了同名注解的方法，范围失控。
5. 如果一个 Mapper 方法既需要自动填充又需要分页，两个 AOP/插件的执行顺序如何确定，会不会互相冲突？答案要点：PageHelper 是 MyBatis 层的 `Interceptor`，作用于 SQL 执行阶段；`AutoFillAspect` 是 Spring AOP，作用于方法调用阶段，二者拦截的时机和维度不同，互不冲突，AutoFill 先在方法调用前填充字段，之后 SQL 才被 PageHelper 拦截改写。

**本单元产出**：学生独立编写一个包含至少三种动态 SQL 标签（`<if>`、`<where>`或`<set>`、`<foreach>`）的 Mapper XML 文件，并独立实现一个自定义注解+AOP 切面完成某项横切逻辑。

## 单元 3：认证鉴权（JWT + Interceptor + ThreadLocal）

**教学目标**：学生能够画出 JWT 的三段式结构并解释每一部分的作用；能够独立实现 JWT 的签发与验签代码；能够说明 `HandlerInterceptor` 的三个生命周期方法及其在鉴权链路中的分工；能够解释 `ThreadLocal` 为什么能在同一次请求的多层调用中传递用户身份，以及为什么必须在请求结束后清理。

**先修知识**：Servlet 基础（Filter/Interceptor 概念）、HTTP 请求头的基本认知、单元 1 中的分层架构、单元 2 中已经初步接触过的 `BaseContext`（在自动填充中用到过 `getCurrentId()`）。

**核心知识讲解**：

JWT（JSON Web Token）由 Header、Payload、Signature 三段组成，以英文句点分隔，各段分别经过 Base64Url 编码。Header 声明签名算法（本项目为 HS256），Payload 携带业务数据（本项目在管理端存 `empId`，用户端存 `userId`），Signature 是服务端用密钥对 Header+Payload 计算出的签名值，用于防止令牌被篡改。整个机制的核心价值在于"无状态"——服务端不需要在内存或数据库中保存"谁登录了"这一会话信息，只要客户端把令牌带回来，服务端用同一份密钥重新计算签名并比对即可验证令牌的合法性与完整性，这与传统 Session 机制"服务端保存会话状态"形成鲜明对比，也解释了为什么 JWT 特别适合分布式、多实例部署的场景（任意一台服务器都能独立验签，不需要共享会话存储）。本项目 `JwtUtil.createJWT()` 方法接收密钥、过期时长（TTL）、Claims 数据，通过 `Jwts.builder().setClaims(claims).signWith(SignatureAlgorithm.HS256, secretKey).setExpiration(expirationDate).compact()` 完成签发；`parseJWT()` 方法通过 `Jwts.parser().setSigningKey(secretKey).parseClaimsJws(token).getBody()` 完成验签并提取数据，验签失败或已过期都会抛出异常。

`HandlerInterceptor` 是 Spring MVC 提供的拦截器接口，包含 `preHandle`（Controller 方法执行前）、`postHandle`（Controller 方法执行后、视图渲染前）、`afterCompletion`（整个请求处理完毕后，无论是否发生异常都会执行）三个生命周期方法。本项目的鉴权拦截器只使用了其中的 `preHandle` 与 `afterCompletion` 两个。`preHandle` 中完成的工作依次是：从请求头（管理端为 `token`，用户端为 `authentication`，两个头名称在 `JwtProperties` 中分别配置，互不相同）取出令牌，调用 `JwtUtil.parseJWT()` 验签并提取用户标识，管理端额外增加了一步数据库复核——通过 `employeeMapper.getById(empId)` 查询该员工当前状态，如果员工已被禁用，即便令牌本身合法且未过期，也直接返回 401 拒绝访问，这一步是对纯 JWT 无状态方案的重要补强，因为纯粹的无状态方案无法在令牌有效期内"撤销"某个已签发的令牌，本项目通过"每次请求都查一次账号状态"这一相对轻量的代价，换来了"禁用立即生效"的安全能力。验证通过后，调用 `BaseContext.setCurrentId(empId)` 将用户标识写入线程局部变量。`afterCompletion` 中调用 `BaseContext.removeCurrentId()` 完成清理，这一步绝不能省略——Tomcat 处理 HTTP 请求使用的是线程池，线程会被反复复用处理不同请求，如果不清理，下一个请求可能会读到上一个请求遗留的用户 ID，造成极其严重的身份混淆事故，这也是本单元与操作系统课程"线程复用"知识点的直接呼应点。

`BaseContext` 封装了一个 `ThreadLocal<Long>` 静态变量，之所以能在 Controller、Service、Mapper 各层之间"隔空传递"用户身份，本质是因为它们都在同一个线程内被顺序调用——ThreadLocal 的存储不是全局共享，而是每个线程各自持有一份独立副本，因此在同一线程内的任意方法都可以读到同一份数据，而不同线程（对应不同的并发请求）之间互不干扰，天然线程安全，无需加锁。教师应特别指出 Agent 模块中的一个例外情况：`AgentController.stream()` 接收到请求后，会把实际的业务处理（`agentChatService.chat()`）提交到独立的线程池（`agentExecutor`）中异步执行，由于这是一个新的线程，原来 Servlet 容器线程中设置的 `BaseContext` 值不会自动带过去，所以 `AgentController` 必须先在提交任务之前读出 `empId`（`BaseContext.getCurrentId()`），再把它作为参数显式传递给异步任务，任务内部（`AbstractSkill.invoke()`）在真正执行业务前重新调用 `BaseContext.setCurrentId(empId)`，执行完毕后在 `finally` 块中调用 `removeCurrentId()`。这个细节是检验学生是否真正理解 ThreadLocal"线程绑定"本质的最佳考点。

**代码实操指引**：

要求学生完成：第一步，使用在线 JWT 调试工具（或者自己写一段代码）解码一枚从本项目登录接口拿到的真实令牌，观察 Header 和 Payload 的明文内容，理解"JWT 不加密只签名"这一常被误解的知识点（Payload 是 Base64 编码而非加密，任何人都能解码看到内容，因此绝不能把密码等敏感信息放进 Payload）；第二步，在 Postman 中手动构造一个过期的令牌（可以通过修改本地时间或者等待真实过期）发起请求，观察拦截器返回 401 的完整过程，并用调试器单步跟踪 `parseJWT()` 抛出异常的具体位置；第三步，在管理后台禁用某个测试员工账号，使用该员工此前登录时获得的、尚未过期的令牌发起请求，验证"禁用立即生效"这一安全设计确实生效；第四步，仿照现有拦截器，独立实现一个只作用于某个新增业务模块路径的拦截器并在 `WebMvcConfiguration` 中注册。

**易错点/常见误区**：

最常见的误区是把 JWT 理解为"加密的令牌"，进而认为可以放任意敏感信息进去，教师必须反复纠正——JWT 的 Payload 只是签名保护、并未加密，任何持有令牌的人都能用浏览器控制台的 `atob()` 函数直接解码出明文内容，因此密码、身份证号等敏感字段绝对不能出现在 JWT Payload 中。第二个常见误区是认为"令牌没过期就一定代表用户仍然有权限"，忽视了本项目在拦截器里做的账号状态复核，学生做课程设计时如果照搬"只验签不查库"的简化方案，会做出一个无法及时收回权限的系统。第三个常见误区是忘记在拦截器或者异步任务的 `finally` 块中清理 `ThreadLocal`，教师应通过构造一个"清理代码被异常绕过"的场景（例如在 `removeCurrentId()` 之前的代码抛出异常导致该行代码从未执行）来展示为什么必须用 `try-finally` 而不是简单的顺序代码。

**面试真题**：

1. 请描述 JWT 认证的完整流程，包括签发、传递、验签三个阶段。答案要点：登录成功后服务端用密钥对 Header+Payload 签名生成 Token；客户端后续每次请求在约定的请求头中携带该 Token；服务端拦截器用同一密钥重新验签并提取 Payload 中的用户标识，验证失败返回 401。
2. JWT 与传统 Session 机制相比，各自的优缺点是什么？答案要点：JWT 无状态、天然支持分布式、服务端无存储压力，但存在令牌一旦签发难以主动失效的问题；Session 依赖服务端存储会话状态，多实例部署需要共享存储（如 Redis）或者会话粘滞，但可以随时通过删除会话让用户立即下线。
3. 本项目是如何解决"JWT 无法主动失效"这一固有缺陷的？答案要点：管理端拦截器在验签通过之后，额外查询数据库校验员工的启用/禁用状态，被禁用的账号即便持有合法未过期令牌也会被拒绝访问，用一次数据库查询的代价换来"准实时"的权限撤销能力。
4. ThreadLocal 是如何做到线程安全的？在什么场景下会出现内存泄漏？答案要点：每个线程维护一份独立的 `ThreadLocalMap`，读写只作用于当前线程自己的副本，因此不需要加锁；如果使用线程池且忘记调用 `remove()`，由于线程会被复用并长期存活，对应的 value 对象会一直被该线程的 `ThreadLocalMap` 强引用而无法被垃圾回收，造成内存泄漏，同时还会引发数据串号的业务隐患。
5. 为什么本项目管理端和用户端要使用两套完全独立的 JWT 密钥和请求头名称？答案要点：管理端和用户端是权限完全不同的两套身份体系，如果共用密钥，一旦某一端的密钥泄露，攻击者可以伪造另一端的令牌；使用不同的请求头名称（`token` 与 `authentication`）进一步降低两端令牌被混用的概率，属于纵深防御思想的体现。

**本单元产出**：学生独立实现一套最小可用的 JWT 签发/验签工具类，并配合一个 `HandlerInterceptor` 完成对指定路径的鉴权保护，同时正确处理 ThreadLocal 的设置与清理。

## 单元 4：业务逻辑（订单全生命周期 + 状态机）

**教学目标**：学生能够独立画出订单状态机的完整状态迁移图并说明每条边对应的触发条件；能够解释为什么订单金额必须在服务端重新计算而不能信任客户端传入值；能够说明支付回调场景下"幂等性"的含义与实现方式；能够解释定时任务在业务闭环中承担的兜底职责。

**先修知识**：单元 1-3 建立的分层架构、鉴权链路知识，数据库事务基本概念（ACID），有限状态自动机的基本思想（若学生此前未系统学过，教师需要用本单元现场补齐）。

**核心知识讲解**：

状态机是对"一个对象在其生命周期内只能按照特定规则从一种状态转换到另一种状态"这一约束的形式化描述。本项目订单实体的状态字段定义了六个取值：待付款（1）、待接单（2）、已接单（3）、派送中（4）、已完成（5）、已取消（6），前五个状态构成一条主干迁移链（1→2→3→4→5），已取消状态则可以从除已完成之外的任意非终态转入，代表订单在流程中被中途终止。教师应引导学生认识到，状态机的价值不在于"记录当前是哪个状态"，而在于"约束哪些状态转换是合法的、哪些是非法的"——例如一个还处于"待付款"状态的订单，是不允许直接被"接单"操作的，必须先经过支付回调把状态推进到"待接单"。本项目在 `OrderServiceImpl` 中的每一个状态转换方法（`confirm()` 接单、`rejection()` 拒单、`cancel()` 取消、`delivery()` 派送、`complete()` 完成）内部，第一步永远是查询订单当前状态并进行前置校验，只有满足"当前状态允许该操作"的前提下才会真正执行状态更新，否则抛出业务异常。教师应把这些校验逐一列出并要求学生对照代码验证：接单要求当前状态为"待接单"；拒单同样要求"待接单"（因为已经接单的订单不能反悔拒单，只能走取消流程）；派送要求当前状态为"已接单"；完成要求当前状态为"派送中"；取消则要求订单尚处于非终态（既未完成也未取消）。

金额服务端重算是本单元最重要的安全与业务准确性话题。用户下单时，前端提交的 `OrdersSubmitDTO` 只包含地址、支付方式、备注等与"钱"无关的信息，绝不包含金额字段，即便客户端恶意构造请求体强行塞入一个金额字段，服务端也完全不会读取它。真正的金额计算发生在 `OrderServiceImpl.submitOrder()` 内部，遍历当前用户购物车中的每一项记录，将其 `amount`（单价，且这个单价本身也是加购物车时从数据库菜品/套餐表读取写入的，同样不信任客户端）乘以 `number`（数量）后累加，再加上打包费，得到最终的订单实收金额。这一设计原则可以归纳为一句工程格言："凡是涉及金钱的字段，一律不信任客户端传入值，必须以服务端持久化的权威数据为唯一依据重新计算"，教师应结合真实的电商刷单/篡改价格攻击案例，让学生理解这不是理论上的"最佳实践"，而是关乎真实经济损失的生死线。

支付回调的幂等性设计解决的问题是：微信支付服务器在网络异常时可能对同一笔支付结果重复发起多次回调通知，如果服务端每次收到回调都不假思索地执行一次"订单状态从待付款推进到待接单"的更新，第二次及以后的重复回调理应被安全地忽略掉，而不能因为重复执行导致状态机被破坏（例如已经处于"已接单"状态的订单又被回调逻辑强行拉回"待接单"）。本项目 `paySuccess()` 方法在真正执行状态更新之前，先查询订单当前状态，如果发现订单已经不是"待付款"状态（说明此前的回调已经处理过），直接返回成功而不做任何数据修改，这种"先检查当前状态是否满足前置条件、不满足则直接短路返回"的写法，是实现幂等性的通用范式，教师应强调这一范式同样适用于其他任何可能被重复触发的写操作（例如消息队列的重复消费场景）。回调报文本身使用 AES-GCM 算法加密（对应微信支付 APIv3 的加密回调机制），服务端必须先用商户配置的 APIv3 密钥解密得到明文 JSON，再从中提取商户订单号（`out_trade_no`）进行后续业务处理，教师可以借此简单科普对称加密算法在真实支付系统中的实际应用场景。

定时任务承担的是业务流程中"异常兜底"的角色，而非主干流程。本项目 `OrderTask` 中定义了两个 `@Scheduled` 方法：一个每分钟执行一次，扫描所有下单超过 15 分钟仍处于"待付款"状态的订单，自动将其状态更新为"已取消"，其存在的意义是防止用户下单后既不支付也不主动取消，导致订单永久滞留在待付款状态占用库存或者干扰统计报表；另一个每天凌晨 1 点执行一次，扫描所有处于"派送中"状态超过 60 分钟的订单，自动将其标记为"已完成"，用于处理配送员忘记在系统中手动确认送达的边缘情况。教师应强调，这类定时任务的设计思路是"给正常业务流程之外的异常情况设置一道安全网"，而不是替代正常的用户/商家操作，学生在设计自己的系统时应养成"每一个可能卡死的状态都要考虑是否需要兜底机制"的习惯。

**代码实操指引**：

要求学生完成：第一步，独立画出订单状态机的完整状态迁移图（建议用箭头图或表格形式），并逐条对照 `OrderServiceImpl` 中六个状态转换方法验证图与代码的一致性；第二步，在测试环境模拟一次完整下单流程，在数据库层面全程观察 `orders` 表和 `order_detail` 表数据的插入过程，并尝试篡改客户端请求体中的金额字段（如果前端表单允许修改），验证服务端确实忽略了该字段；第三步，模拟微信支付回调重复调用两次，验证第二次调用不会导致订单状态异常或者商家被重复推送来单通知；第四步，手动将某条测试订单的 `order_time` 改到 20 分钟前并将状态设为待付款，等待定时任务执行（或手动触发对应方法），验证订单确实被自动取消。

**易错点/常见误区**：

学生在自己实现类似状态机时，最常见的错误是"只在 Controller/前端层面禁用不合法操作的按钮"，而忘记在 Service 层做后端强制校验，这是典型的"防君子不防小人"的伪安全设计——只要有人直接用 Postman 绕过前端按钮发起请求，未做后端校验的状态机形同虚设。第二个常见错误是把金额计算逻辑做成"前端算好、后端只负责存储"，教师应结合本单元的重算原则反复纠正。第三个常见错误是幂等性设计遗漏，学生初次实现支付回调逻辑时往往只考虑"正常收到一次回调"的情况，没有考虑网络重试导致的重复回调，这类 Bug 往往在生产环境高并发/网络不稳定场景下才会暴露，平时测试很难发现，因此更需要在设计阶段就养成习惯。

**面试真题**：

1. 请画出本项目订单状态机的状态迁移图，并说明"取消"状态的特殊性。答案要点：主干链路为待付款→待接单→已接单→派送中→已完成，取消可以从除已完成外的任意非终态转入，是一个"旁路终态"，代表流程被中途中断而非正常走完全程。
2. 为什么订单金额不能由前端传给后端，而必须由后端重新计算？答案要点：客户端完全可控，任何前端传入的数值都可能被篡改，涉及金钱的计算必须以服务端持久化的权威数据（数据库中的商品单价）为唯一依据重新计算，否则存在被刷单牟利的严重安全漏洞。
3. 什么是接口的幂等性？请结合本项目支付回调场景说明如何实现。答案要点：幂等性指同一个操作无论被执行一次还是多次，最终产生的效果都相同；本项目在处理支付回调时，先检查订单当前状态是否仍为待付款，若已经被处理过（状态已推进）则直接返回成功而不重复执行状态更新，避免了重复回调对状态机造成破坏。
4. 定时任务在本项目中解决了什么问题？如果没有定时任务会出现什么后果？答案要点：定时任务处理"用户下单不支付""配送员忘记标记完成"等边缘异常情况，如果没有定时任务，订单可能永久滞留在某个中间状态，污染统计报表并占用系统资源。
5. 如果要新增一个"用户催单"功能，应该在订单状态机的哪个环节插入，需要注意什么？答案要点：催单通常发生在"已接单"或"派送中"阶段，本身不改变订单状态，只是触发一次 WebSocket 通知推送给商家端，设计时需要注意催单频率限制，避免用户短时间内重复点击催单造成骚扰式推送。

**本单元产出**：学生提交一份完整的订单状态机图纸（图或表格均可）以及一段模拟测试报告，记录自己动手验证金额重算、支付回调幂等性、定时任务兜底三项机制的实际过程与观察结果。

## 单元 5：缓存与实时通信（Redis + WebSocket）

**教学目标**：学生能够根据业务场景正确选择 Redis 数据结构；能够解释 `@Cacheable`/`@CacheEvict` 声明式缓存注解背后发生的动作；能够说明为什么清理缓存要用 `SCAN` 而不是 `KEYS`；能够独立搭建一个基于 `@ServerEndpoint` 的 WebSocket 广播服务。

**先修知识**：单元 1-4 建立的分层架构与业务闭环认知，键值存储的基本概念（数据库课程中通常会简单提及 NoSQL）。

**核心知识讲解**：

Redis 之所以能够作为缓存层大幅提升系统性能，根本原因在于它是纯内存数据库，读写操作不涉及磁盘 I/O，延迟通常在微秒到毫秒级别，远低于关系型数据库的磁盘 I/O 延迟。但缓存不是免费的午餐，引入缓存意味着系统必须处理"缓存与数据库数据不一致"这一新增复杂度，本项目在这一点上给出了两种典型的处理策略。策略一是"永不过期 + 主动同步"，店铺营业状态存储在 Redis 的一个固定键（`SHOP_STATUS`）中，没有设置过期时间，任何对营业状态的修改（`ShopServiceImpl.setStatus()`）都直接写入 Redis 且没有中间状态，这种策略适合"低频修改但高频读取、且必须强一致"的场景。策略二是"主动清除 + 惰性回填"，菜品数据按分类 ID 缓存（键格式 `dish_{categoryId}`），管理端对菜品做任何增删改操作后，立即清除该分类对应的缓存键，下一次 C 端用户查询时缓存未命中，程序重新查询数据库并把结果回写进缓存，这种策略适合"读多写少、允许短暂缓存缺失、但绝不允许长期脏数据"的场景。教师应引导学生思考：为什么菜品缓存不能用"设置一个较短的过期时间、让它自然失效"这种更简单的方案？因为过期时间的选择本质是在"数据新鲜度"和"缓存命中率"之间做权衡，设置过短则失去了缓存的意义，设置过长则管理端修改菜品后 C 端要等很久才能看到最新数据，而主动清除方案可以做到"修改立即生效、未修改时缓存持续有效"，是更优的工程选择。

清理缓存时使用 `SCAN` 命令而非 `KEYS` 命令是一个容易被忽视但在生产环境中至关重要的细节。`KEYS pattern` 命令会一次性遍历 Redis 整个键空间并返回所有匹配的键，由于 Redis 是单线程模型，这个遍历过程会阻塞主线程，如果键空间很大（几十万甚至上百万个键），`KEYS` 命令可能导致 Redis 在执行期间对所有其他客户端请求都无响应，造成生产事故；`SCAN cursor MATCH pattern COUNT count` 命令则采用游标分批遍历的方式，每次只扫描一小部分键空间并返回一个新的游标供下次调用，不会长时间阻塞主线程，虽然单次 `SCAN` 的时间复杂度和最终效果与 `KEYS` 相近，但通过分批执行避免了"长时间占用单线程"这一致命问题。本项目在清除菜品缓存时使用 `ScanOptions.scanOptions().match(pattern).count(100).build()` 构造扫描选项，体现了对生产级 Redis 使用规范的重视，教师应结合 Redis 单线程模型的原理讲清楚这一细节背后的完整逻辑链，而不是让学生死记"`SCAN` 比 `KEYS` 好"这一结论。

`@Cacheable` 与 `@CacheEvict` 是 Spring Cache 提供的声明式缓存注解，其工作机制建立在 AOP 之上——被 `@Cacheable` 标注的方法在被调用时，Spring 生成的代理对象会先检查缓存中是否已存在以指定 key 为标识的数据，如果存在直接返回缓存值、不再执行方法体（即不查数据库），如果不存在才真正执行方法体并将返回结果自动写入缓存；`@CacheEvict` 标注的方法在执行完毕后，会自动清除指定 key 对应的缓存项。这与本项目在 `AutoFillAspect` 中手写 AOP 切面是同一套底层机制的不同应用——一个是框架已经封装好的声明式用法，一个是开发者自己实现的定制化切面，教师应引导学生把这两处知识点关联起来，理解"AOP 是一种通用的编程范式，声明式缓存只是这个范式在缓存场景下的一种具体实现"。

WebSocket 之所以适合"来单提醒"这一场景，根本原因在于它是全双工的长连接协议，一旦建立连接，服务端可以在任意时刻主动向客户端推送消息，不需要客户端每次轮询请求"有没有新订单"。本项目 `WebSocketServer` 使用 JSR-356 标准的 `@ServerEndpoint("/ws/{sid}")` 声明一个 WebSocket 端点，`{sid}` 作为路径变量用于唯一标识每一个连接（通常是每个打开管理后台页面的浏览器标签页对应一个 sid），三个生命周期回调方法 `@OnOpen`、`@OnMessage`、`@OnClose` 分别在连接建立、收到客户端消息、连接关闭时被容器自动调用。所有活跃连接的 `Session` 对象被存储在一个静态的 `Map<String, Session>` 中，`sendToAllClient()` 方法遍历这个 Map，对每一个 Session 调用 `getBasicRemote().sendText()` 完成广播，这本质上就是单元 1 中提到的哈希表在真实工程场景中的具体应用——用 sid 作为 key 是为了支持未来可能出现的"定向推送给某个特定连接"的需求，即便当前版本只用到了广播这一种能力。

**代码实操指引**：

要求学生完成：第一步，使用 `redis-cli` 连接本地 Redis 实例，手动执行 `GET SHOP_STATUS`、`KEYS dish_*` 等命令，观察本项目实际写入的缓存键与值，建立对"抽象概念"与"真实存储内容"的直接对应关系；第二步，在管理后台修改一个菜品的价格，立即用 `redis-cli` 观察对应缓存键是否被清除，随后在用户端小程序（或模拟接口调用）查询该分类菜品，验证缓存重新回填后的数据是否正确更新；第三步，独立实现一个简单的 `@Cacheable` 缓存示例并观察方法体是否在缓存命中时被跳过执行（可以在方法体内打印日志辅助验证）；第四步，打开两个浏览器标签页同时登录管理后台，模拟一次用户下单支付成功，观察两个标签页是否都收到 WebSocket 推送的来单提醒弹窗。

**易错点/常见误区**：

学生常见的误区之一是认为"只要用了 Redis 缓存，系统性能就一定会变好"，而忽视了"缓存一致性维护成本"这一隐性代价，教师应引导学生认识到缓存是有代价的工程决策，只应用在真正的热点数据或高频只读数据上，不应该"逢查询必加缓存"。误区之二是把 `KEYS` 命令当作日常运维和业务代码中的常规操作，只在生产环境出现性能问题后才意识到问题，教师应提前把这一坑讲清楚，避免学生在未来的实习或工作中踩雷。误区之三是把 WebSocket 连接的生命周期管理想得过于简单，忽视了浏览器标签页关闭、网络波动导致连接异常断开等场景下 `sessionMap` 可能残留失效 Session 的问题，本项目通过 `@OnClose` 回调及时清理，教师应提醒学生在设计类似系统时必须对连接的"非正常终止"场景有预案。

**面试真题**：

1. 请说明本项目菜品缓存的清除时机和回填时机，为什么不设置一个固定的过期时间？答案要点：管理端增删改菜品后立即清除对应分类缓存，C 端下一次查询时缓存未命中则查库并回填；固定过期时间无法保证"修改后立即生效"，主动清除策略在保证数据新鲜度和缓存命中率之间取得更好的平衡。
2. `KEYS` 和 `SCAN` 命令有什么区别，为什么生产环境要避免使用 `KEYS`？答案要点：`KEYS` 一次性全量遍历键空间且阻塞 Redis 单线程，键空间大时会造成长时间无响应；`SCAN` 基于游标分批遍历，不会长时间占用主线程，适合生产环境使用。
3. `@Cacheable` 注解的底层实现原理是什么？答案要点：基于 Spring AOP 生成代理对象，方法调用时代理先查缓存，命中则直接返回、不执行原方法体，未命中则执行原方法体并将结果自动写入缓存。
4. 为什么来单提醒使用 WebSocket 而不是让前端定时轮询查询是否有新订单？答案要点：轮询存在延迟（取决于轮询间隔）且会产生大量无效请求浪费服务器资源；WebSocket 建立长连接后服务端可以在事件发生的瞬间主动推送，实时性更好且资源消耗更低。
5. 如果 WebSocket 连接异常断开（比如用户关闭浏览器或网络中断）而没有正常触发 `@OnClose`，会有什么后果，如何缓解？答案要点：`sessionMap` 中会残留一个失效的 Session 引用，后续广播时对该 Session 调用 `sendText()` 会抛出异常，本项目在 `sendToAllClient()` 中用 `try-catch` 包裹单次发送操作，避免一个失效连接的异常中断对其他正常连接的广播，工程上还可以考虑心跳检测机制主动探测并清理失效连接。

**本单元产出**：学生提交一份 Redis 键值观察记录（截图或文本记录均可）以及一次完整的 WebSocket 广播联调测试报告（至少两个客户端同时收到广播消息的证明）。

## 单元 6：文件上传与第三方集成（OSS + 百度地图 + 微信）

**教学目标**：学生能够独立实现一个具备安全校验（大小限制、扩展名白名单、文件名防碰撞）的文件上传接口；能够说明为什么第三方 API 调用需要做超时和异常处理；能够解释微信小程序静默登录（`code`换`openid`）的完整流程。

**先修知识**：单元 1-5 全部内容，HTTP 客户端调用的基本概念（GET/POST 请求、请求参数构造）。

**核心知识讲解**：

文件上传接口看似简单，实则是系统安全防线中极易被忽视的一环，本项目 `CommonController.upload()` 的实现体现了三层防御。第一层是大小限制，通过配置项 `sky.upload.max-size-bytes`（默认 5MB）校验上传文件体积，防止恶意用户上传超大文件占满服务器磁盘或带宽资源，这是最基础的资源保护措施。第二层是扩展名白名单校验，只允许 `jpg/jpeg/png/gif/webp` 五种图片格式通过，任何其他扩展名（尤其是 `.jsp`、`.php`、`.exe` 等可执行文件后缀）一律拒绝，这一防线的意义在于防止攻击者伪装成"上传图片"实际上传可执行脚本，一旦服务器错误地将上传目录配置为可执行目录，攻击者上传的恶意脚本文件可能被服务器直接解析执行，造成远程代码执行这类最高危害等级的安全漏洞。第三层是文件名重命名，本项目使用 `UUID.randomUUID()` 生成全新的文件名而不使用客户端原始文件名，这样做同时解决了两个问题：一是防止不同用户上传同名文件互相覆盖，二是防止客户端在文件名中构造路径穿越字符串（例如 `../../etc/passwd`）尝试访问或覆盖服务器上的其他目录文件。教师应把这三层防御作为一个完整的检查清单教给学生，强调"文件上传功能只要遗漏其中任何一层，都可能演变成严重的安全漏洞"，这是业界真实发生过大量安全事故的高风险功能点。

阿里云 OSS（对象存储服务）被选用作为图片的最终存储位置，而不是直接存储在应用服务器本地磁盘，这一架构决策同样值得讲解：应用服务器本地磁盘存储图片存在多个问题——第一，如果系统未来需要水平扩展为多台服务器，本地存储的图片无法被其他服务器节点访问，导致图片时而能看到时而看不到；第二，应用服务器的磁盘容量有限，图片文件持续增长最终会耗尽磁盘空间影响应用本身的运行；第三，本地文件缺乏专业存储系统提供的高可用、多副本容灾能力。将图片上传至独立的对象存储服务，应用服务器只需保存图片的访问 URL 而不保存图片本体，从架构上实现了"计算与存储分离"，这是现代云原生应用的标准实践，`AliOssUtil.upload()` 封装了这一层对接细节，教师应带学生阅读该工具类，理解它是如何把字节数组和目标文件名传递给阿里云 SDK 并拿到最终可访问 URL 的。

配送范围校验展示了一个典型的"多个外部 API 组合调用"场景。要判断用户的收货地址是否在店铺配送范围内，系统需要先通过百度地图的 Geocoding（地理编码）API 把店铺地址和用户地址这两个文本字符串分别转换为经纬度坐标，再通过路线规划 API 计算两点之间的实际驾车距离（而非直线距离，因为真实配送路径受道路网络约束），最后将计算出的距离与阈值（本项目设定 5000 米）比较决定是否允许下单。教师应引导学生注意工程细节：当百度地图 AK（Access Key）未配置时，本项目选择"跳过该校验"而不是"直接报错阻断下单流程"，这是一种优雅降级（Graceful Degradation）的设计思路——第三方服务不可用或未配置时，系统应尽量保证核心业务流程不中断，而不是让一个非核心的辅助校验环节拖垮整个下单功能，这一设计哲学同样应该体现在其他任何依赖外部服务的功能模块中。

微信小程序登录采用的是"静默登录"模式，用户无需输入账号密码，只需在小程序端调用 `wx.login()` 获取一个临时的 `code`（有效期很短，仅用于换取身份标识），后端拿到这个 `code` 后调用微信官方接口 `https://api.weixin.qq.com/sns/jscode2session` 用 `code` 加上小程序的 `appid`/`secret` 换取该用户的 `openid`（微信为每个用户在每个小程序下分配的唯一标识）。本项目 `UserServiceImpl.wxLogin()` 拿到 `openid` 后，先查询本地用户表是否已存在该 `openid` 对应的记录，若不存在则视为该用户第一次使用本小程序，自动插入一条新用户记录完成"注册"，这种"首次登录即自动注册"的设计极大降低了小程序场景下的用户使用门槛，是移动端产品设计的常见范式。教师应强调 `openid` 本身并不包含任何用户的真实身份信息（如手机号、姓名），它只是微信平台内部为区分不同用户而生成的匿名标识，如果业务需要获取用户的手机号等信息，需要用户额外授权，这一点也是数据隐私保护原则在实际产品设计中的具体体现。

**代码实操指引**：

要求学生完成：第一步，测试文件上传接口，分别构造"超过大小限制的文件""扩展名为 `.php` 的伪造图片文件""正常图片文件"三种请求，验证三层防御是否分别正确生效；第二步，观察 OSS 返回的图片 URL，理解 URL 中包含的 Bucket 名称、Endpoint、对象路径三部分分别对应什么含义；第三步，在有百度地图 AK 配置和无配置两种环境下分别测试下单流程，验证优雅降级逻辑是否按预期工作；第四步，使用微信开发者工具的小程序模拟器完整走一遍登录流程，观察 `code` 到 `openid` 转换的网络请求细节（可借助浏览器/开发者工具的网络面板）。

**易错点/常见误区**：

学生实现文件上传功能时最常犯的错误是只做前端的文件类型限制（例如 HTML `<input accept="image/*">`），却忘记在后端再做一次校验，教师必须强调"前端校验只是用户体验优化，后端校验才是安全的最后一道防线"，因为前端限制可以被绕过（直接用 Postman 构造请求）。第二个常见误区是文件名重命名时只是简单地在原文件名前加一个随机数前缀，而没有完全抛弃原文件名，这样仍然残留了路径穿越攻击的风险，正确做法是完全丢弃客户端提供的原始文件名，只保留合法的扩展名部分与全新生成的 UUID 文件名拼接。第三个常见误区是调用第三方 API 时没有设置超时时间，一旦第三方服务响应缓慢或者无响应，会导致当前请求线程被无限期挂起，进而拖垮整个应用的线程池资源，本项目中的 `HttpClientUtil` 已经封装了合理的超时配置，教师应提醒学生在任何自己编写的外部 API 调用代码中都要显式设置连接超时和读取超时。

**面试真题**：

1. 文件上传功能应该做哪些安全校验？请结合本项目说明每一层校验分别防御什么攻击。答案要点：大小限制防止资源耗尽攻击，扩展名白名单防止上传可执行脚本导致远程代码执行，UUID 重命名防止文件覆盖和路径穿越攻击，三层防御缺一不可。
2. 为什么系统选择把图片存储在阿里云 OSS 而不是应用服务器本地磁盘？答案要点：实现计算与存储分离，支持未来的多实例水平扩展，避免本地磁盘容量瓶颈，享受专业存储服务的高可用能力。
3. 请描述微信小程序静默登录的完整流程。答案要点：小程序端调用 `wx.login()` 获取临时 `code`，传给后端，后端用 `code`+`appid`+`secret` 调用微信官方接口换取 `openid`，本地查询该 `openid` 是否已注册，未注册则自动创建用户记录，最终签发本系统自己的 JWT 返回给小程序端。
4. 配送范围校验依赖百度地图 API，如果该服务暂时不可用，系统应该如何处理？答案要点：应采取优雅降级策略，跳过该项非核心校验而不阻断整个下单主流程，保证核心业务的可用性优先于辅助功能的完整性。
5. `openid` 和用户在系统里的手机号、姓名有什么关系？为什么不能仅凭 `openid` 获取用户手机号？答案要点：`openid` 只是微信为区分用户而生成的匿名标识，本身不包含任何真实身份信息，获取手机号等敏感信息需要用户额外主动授权，这是移动端隐私保护的基本原则。

**本单元产出**：学生提交一份完整的第三方集成测试报告，涵盖文件上传三层防御的验证记录、配送范围校验在有/无 AK 两种场景下的行为对比、微信登录流程的网络请求截图三部分内容。

## 单元 7：Agent 核心——LangChain4j 工具调用与 SSE 流式

**教学目标**：学生能够解释 `AiServices` 声明式编程范式的工作原理；能够独立编写一个包含 `@Tool` 方法的 Skill 类并说明参数类型选择的理由；能够说明 SSE 协议的报文格式与浏览器端解析方式；能够解释为什么 Skill 类不做成 Spring Bean 却依然能享受到 AOP 增强。

**先修知识**：单元 1-6 全部内容（尤其是分层架构与 AOP 代理原理），对大语言模型 Function Calling 机制的基本认知（教师可视学生情况用 10-15 分钟补充背景知识）。

**核心知识讲解**：

LangChain4j 的 `AiServices` 是一种声明式编程范式的具体实现，其编程体验类似于 MyBatis 的 Mapper 接口——开发者只需要定义一个 Java 接口（本项目为 `AgentAssistant`），在方法上用注解声明意图，具体的实现代码由框架在运行时通过动态代理自动生成，开发者永远不需要手写"组装请求消息、调用大模型 API、解析流式响应、判断是否需要调用工具、执行工具方法、把工具结果重新塞回对话上下文继续生成"这一整套繁琐的底层逻辑。本项目 `AgentAssistant` 接口只定义了一个方法：`TokenStream chat(@MemoryId String conversationId, @UserMessage String userMessage)`。`@MemoryId` 标注的参数告诉框架"这个值用来区分不同的会话，不同会话应该拥有独立的对话历史"；`@UserMessage` 标注的参数就是本轮真正的用户输入内容；接口上还标注了 `@SystemMessage`，其内容是一段固定的系统提示词，用于约束模型的行为边界（本项目中包含"禁止编造数据""必须调用工具获取真实数据""不回答敏感问题"等六条规则）。返回类型 `TokenStream` 表明这是一个流式接口，框架不会等模型生成完整回复后一次性返回，而是随着模型逐字生成，实时把每个 token 推送给调用方。

Function Calling（函数调用）机制是让大语言模型能够"操作真实系统"而不仅仅是"生成文本"的关键技术。其完整流程可以概括为：开发者用 `@Tool` 注解标注若干普通 Java 方法（本项目中如 `OrderSkill.confirmOrder()`），并用注解内容描述这个方法的用途，用 `@P` 注解描述每个参数的含义；LangChain4j 框架在启动装配阶段，通过反射扫描这些被注解标记的方法，自动生成符合大模型服务商 Function Calling 协议规范的 JSON Schema 描述（本质是一份"工具说明书"）；每次向大模型发起请求时，这份工具说明书会随对话历史一起发送给模型；模型在生成回复时，会根据用户意图自主判断"这次回复是否需要调用某个工具"，如果需要，模型不会直接生成自然语言文本，而是生成一段结构化的 `tool_calls` 数据（包含要调用哪个工具、传入什么参数）；LangChain4j 框架解析出这段结构化数据后，找到对应的 Java 方法并通过反射真正执行它，将方法的返回值重新作为一条特殊角色（`tool`）的消息追加进对话历史，再次发送给模型；模型基于工具的真实执行结果继续生成最终面向用户的自然语言回复。这个过程可能循环多轮（模型可以连续调用多个工具后才给出最终答案），教师应用一个具体例子演示：当员工询问"帮我查一下订单 1001 的详情"，模型识别出需要调用 `getOrderDetail` 工具、提取出参数 `orderId=1001`，框架执行 `OrderSkill.getOrderDetail("1001")` 得到订单详情文本，模型再把这段文本组织成通顺的自然语言回复给员工。

Skill 层的架构设计是本单元的教学重点与难点。本项目的 `OrderSkill`、`ReportSkill`、`WorkspaceSkill`、`ShopSkill` 四个类都不是 Spring Bean，而是在 `AgentChatService.chat()` 方法内部，针对每一次用户请求通过 `new` 关键字现场创建的普通 Java 对象。教师应引导学生思考三个层层递进的设计动因。第一，每个 Skill 实例的构造函数都接收 `AgentEventSink sink` 和 `Long empId` 两个"请求级"的状态——`sink` 是当前这次 SSE 请求专属的事件推送通道，`empId` 是发起本次对话的员工身份，这两样东西天然是"一次请求一份"，如果把 Skill 做成单例 Spring Bean，就必须用某种方式（例如再套一层 ThreadLocal）在多个并发请求之间隔离这些状态，反而增加了复杂度，直接 `new` 一个新对象是最直接、最不容易出错的方案。第二，LangChain4j 的 `AiServices.builder().tools(...)` 方法要求传入具体的对象实例而非类，框架通过反射扫描传入实例所属类上的 `@Tool` 方法并绑定，这就决定了 Skill 必须先实例化才能被注册为工具集合。第三，也是最容易被学生忽视的一点：虽然 `OrderSkill` 自身是普通对象而非 Spring 代理，但它构造函数接收的 `OrderService orderService` 参数，是由 `AgentChatService` 通过 `@Autowired` 从 Spring 容器中注入进来的，而 Spring 容器中管理的 `OrderService` 实现类实例，恰恰是被 AOP 增强过的代理对象（承载着 `@Transactional` 事务管理、可能存在的缓存注解等横切逻辑）。因此当 `OrderSkill.confirmOrder()` 内部调用 `orderService.confirm(dto)` 时，实际上调用的是这个代理对象的方法，事务照常生效、缓存清理照常执行，AOP 增强完全没有被绕过。这个设计细节完美回答了"新对象怎么还能用到别的 Bean 的 AOP 增强"这一初学者极易产生的困惑，教师应要求学生能够独立、完整地复述这一整条推理链。

`@Tool` 方法参数统一使用 `String` 类型而非更符合语义的 `Long`/`Integer` 类型，是一个经过深思熟虑的防御性设计。大语言模型在生成 Function Calling 参数时，本质上是在"猜测"应该填入什么值，完全可能出现模型返回空字符串、返回字面文本 `"null"`、返回非数字文本等各种意料之外的异常输入，如果参数类型直接声明为 `Long`，框架在做参数反序列化时一旦遇到无法转换的值就会抛出异常，直接导致整个工具调用失败甚至中断整轮对话；而声明为 `String` 类型，无论模型返回什么内容都能被正常接收，随后在 Skill 方法内部通过 `AbstractSkill` 基类提供的 `parseId()`、`parseStatus()`、`parseInt()` 等工具方法做安全的手动解析，解析失败时返回 `null` 或默认值，再由业务代码给出"请提供有效的订单数字 id"这样的友好提示，而不是让程序在解析阶段就直接崩溃。教师应把这一设计原则总结为一句话："凡是来自大模型生成内容的输入，永远视为不可信的外部输入，需要在业务代码中做和处理用户表单输入同等级别的校验防御"。

SSE（Server-Sent Events）协议是本单元的另一个核心知识点。它建立在普通 HTTP 协议之上，服务端在响应头中声明 `Content-Type: text/event-stream`，随后不是一次性返回完整响应体后关闭连接，而是保持连接持续打开，每当有新数据产生就以约定的文本格式追加写入响应流；每一条 SSE 消息以 `data:` 为前缀，多行数据可以用多个 `data:` 前缀行表示，一条完整的消息以两个连续的换行符 `\n\n` 结尾用于分隔消息边界。本项目服务端使用 Spring MVC 提供的 `SseEmitter` 类来实现这一协议，`AgentController.stream()` 方法创建 `SseEmitter` 对象后立即返回给 Spring MVC 框架（这一步至关重要，因为只有先把 `SseEmitter` 返回，Servlet 容器才会将该请求标记为异步处理模式，释放处理线程去处理别的请求），真正耗时的模型调用和工具执行逻辑被提交到一个独立的线程池（`agentExecutor`）中异步执行，在这个异步任务内部通过 `AgentEventSink`（对 `SseEmitter` 的封装）持续调用类似 `sink.text(token)`、`sink.toolCall(...)`、`sink.toolResult(...)`、`sink.end()` 的方法把数据写入流。前端使用原生 `fetch` API 而非 `EventSource` 对象来消费这个流，原因是本项目需要在请求中携带自定义的 `token` 请求头做身份鉴权，而浏览器原生 `EventSource` 不支持自定义请求头，`fetch` 拿到 `Response` 对象后通过 `response.body.getReader()` 拿到一个 `ReadableStreamDefaultReader`，循环读取二进制数据块、用 `TextDecoder` 解码为文本、按照 `\n\n` 切分出一条条完整的 SSE 消息、解析出 `data:` 后面的 JSON 内容、根据其中的 `type` 字段（`text`/`tool_call`/`tool_result`/`end`/`error`）分发给不同的界面渲染逻辑。教师应特别对比 SSE 与 WebSocket 在协议层面的关键差异：SSE 是纯粹基于普通 HTTP 长连接的单向推送、可以被 Nginx 等标准反向代理直接透明转发无需特殊配置；WebSocket 需要通过 HTTP `Upgrade` 请求头完成协议升级，握手成功后连接就切换为独立的、不再遵循 HTTP 语义的 TCP 双向通道，这也是为什么本项目为 WebSocket 单独配置了 `WebSocketConfiguration`（注册 `ServerEndpointExporter`），而 SSE 完全复用了标准的 Spring MVC 控制器写法。

**代码实操指引**：

要求学生完成：第一步，在配置了真实大模型 API Key 的环境下，发起一次 Agent 对话请求（例如询问"今天营业额多少"），使用浏览器开发者工具的网络面板观察 SSE 响应流的原始文本内容，找出 `data:` 前缀和消息分隔符；第二步，阅读 `AgentAssistant` 接口和 `AgentChatService.chat()` 方法源码，画出从"用户发消息"到"收到最终自然语言回复"之间，一次完整涉及工具调用的请求所经过的所有方法调用节点；第三步，仿照 `ReportSkill` 或 `WorkspaceSkill`，独立设计并实现一个新的 Skill 类（可以是一个只读查询工具），正确使用 `String` 参数类型与 `AbstractSkill.invoke()` 模板方法；第四步，故意在自己新增的 Skill 工具方法参数中传入非法字符串（如中文文本、空字符串），验证解析失败时是否返回了友好提示而不是抛出异常导致对话中断。

**易错点/常见误区**：

学生最常见的理解误区是把大模型的"工具调用"想象成模型自己直接执行了代码，实际上模型只是生成了一段描述"我想调用哪个工具、传什么参数"的结构化数据，真正的方法执行是由 LangChain4j 框架在服务端完成的，模型本身没有任何代码执行能力，这个误区如果不纠正会导致学生对整套机制的安全边界产生错误认知（例如误以为"模型能直接访问数据库"）。第二个常见误区是不理解为什么 Skill 一定要重新 `new` 而不能设计成单例，教师应结合前文的三层论证反复讲解，检验方式是让学生自己尝试把 Skill 改造成 Spring Bean 单例并思考会遇到什么并发问题（多个用户同时对话时 `sink` 和 `empId` 该赋给谁）。第三个常见误区是认为 SSE 和 WebSocket 可以随意互相替代，教师应强调二者协议层面的本质差异决定了各自的适用边界，选型错误的直接后果是浪费不必要的工程复杂度或者无法满足实际的通信语义需求。

**面试真题**：

1. 请描述大模型 Function Calling 的完整执行流程。答案要点：开发者声明工具方法并生成工具描述发给模型；模型判断是否需要调用工具并返回结构化的调用请求；客户端框架解析并执行对应方法；执行结果作为新的上下文消息回灌给模型；模型基于真实结果生成最终回复；此过程可能多轮循环。
2. 为什么本项目的 Skill 类不做成 Spring 单例 Bean，而是每次请求用 `new` 创建？答案要点：Skill 需要绑定请求级状态（sink、empId），单例会导致并发请求间状态互相污染；`AiServices.builder().tools()` 需要具体实例而非类；即便是新建的普通对象，其内部持有的 Service 依然是 Spring 管理的 AOP 代理对象，事务和缓存等横切逻辑不会被绕过。
3. `@Tool` 方法为什么统一使用 `String` 类型参数而不是更符合语义的数值类型？答案要点：大模型生成的参数值不可信，可能出现空值、非数字文本等异常情况，如果直接用强类型参数会在框架反序列化阶段直接抛异常中断对话；用 `String` 接收后在业务代码内部做安全的手动解析和防呆校验，能够优雅处理各种异常输入。
4. SSE 和 WebSocket 的核心区别是什么？为什么 AI 对话场景选择 SSE？答案要点：SSE 基于普通 HTTP、单向推送、可被标准反向代理透明转发；WebSocket 需要协议升级、全双工双向通信。AI 对话本质是"一次请求、流式接收一段回复"的单向推送模式，不需要客户端在同一连接上主动发送额外消息，SSE 完全满足需求且更轻量。
5. 为什么 `AgentController.stream()` 方法必须先返回 `SseEmitter` 对象，再把真正的业务处理逻辑放到独立线程池中执行？答案要点：只有先返回 `SseEmitter`，Servlet 容器才会把该请求标记为异步处理模式并释放当前处理线程去服务其他请求；如果在返回 `SseEmitter` 之前的同一个线程里直接执行耗时的模型调用，会长时间占用宝贵的 Tomcat 工作线程，在高并发场景下迅速耗尽线程池资源。

**本单元产出**：学生独立实现一个新的 Agent Skill 工具（包含至少一个 `@Tool` 方法），完成从需求描述、参数防呆解析、`invoke()` 模板方法接入、到前端 SSE 卡片正确渲染的完整闭环，并提交一份包含请求-响应完整日志的联调报告。

## 单元 8：Agent 安全与工程化

**教学目标**：学生能够系统性列举 Agent 系统面临的安全风险类别并说明本项目针对每一类风险采取的具体防御手段；能够解释限流算法的基本原理；能够说明有界线程池相比无界线程池的核心优势；能够独立完成一次 Agent 模块的 Nginx 部署配置。

**先修知识**：单元 1-7 全部内容，尤其是单元 3 的鉴权机制、单元 5 的并发安全概念、单元 7 的 Function Calling 与 SSE 机制。

**核心知识讲解**：

将大语言模型接入一个具备真实写操作能力（接单、拒单、开关店等）的生产系统，与单纯做一个"聊天机器人"相比，安全风险的等级完全不同——聊天机器人说错话最多是体验不佳，而 Agent 系统一旦被误导执行了错误的写操作，会直接造成真实的经济损失和业务混乱。本单元系统梳理本项目针对这一新型风险采取的多层防御体系，教师应引导学生认识到"安全不是某一个开关，而是层层叠加的纵深防御"。

第一层防御是**二次确认机制**。教师应重点分析本地模式（无 API Key 时）下的 `AgentPendingActionStore` 设计：当用户输入被识别为一个写操作意图（例如"打烊"），系统并不立即执行 `shopService.setStatus(0)`，而是先把这个待执行的动作（用 Java 8 的函数式接口 `Supplier`/自定义 `Callable` 封装成一个"闭包"）连同工具名、参数一起存入一个以 `empId` 为 key 的临时存储中，并设置 120 秒的存活时间，同时向用户返回一句明确的确认追问；只有当用户在 120 秒内明确回复"确认"类词汇，系统才会取出这个闭包真正执行；如果用户回复"取消"或者干脆说了一句无关的话，待确认动作就会被清除或替换。这一机制的设计动机源于自然语言的天然歧义性——例如用户可能说"能不能别打烊啊"，字面上包含"打烊"这个关键词，但真实意图恰恰是"不要打烊"，如果系统看到关键词就直接执行，会酿成完全相反的严重后果，二次确认机制把"理解意图"和"执行动作"这两个步骤解耦，用一次额外的人工确认为整个系统兜底。教师应要求学生思考：为什么确认动作要设置 120 秒的存活时间而不是永久有效？因为如果用户提出一个写操作请求后中途改变话题聊别的事情，几分钟后一句无关的"确认"不应该意外触发一个用户已经遗忘的旧操作，超时机制降低了这种"误触发"的概率。

第二层防御是**输入与输出的边界控制**，包括单条用户输入长度上限（2000 字）、工具执行结果截断（2000 字符）、以及 `searchOrders` 工具的 `pageSize` 硬编码上限（无论模型传入什么数值，最终都会被 `Math.min(Math.max(parseInt(pageSize, 10), 1), 10)` 这行代码强制夹紧在 1 到 10 之间）。教师应重点剖析 `pageSize` 上限背后的真实攻击场景：如果没有这层限制，一旦模型（无论是被恶意诱导还是自身出现幻觉）传入一个极大的 `pageSize` 值，系统会把大量订单记录（包含顾客手机号等个人敏感信息）一次性查出并作为工具执行结果回灌进模型的上下文，这段包含大量真实用户隐私数据的文本随后会被发送给大模型服务商的服务器，构成一次实质性的数据泄露事件，即便模型本身不会主动"泄露"这些数据给最终用户，数据已经离开了本系统的信任边界这一事实本身就是不可接受的风险，因此在 Skill 层做强制上限拦截，是比"寄希望于模型自己控制好参数"更可靠的工程手段。

第三层防御是**会话隔离**。本项目会话 ID 的生成规则是 `emp:{empId}:{sub}`，前端可以传入一个自定义的子会话标识（`sub`）用于同一员工区分多个并行的对话窗口，但无论前端传入什么值，最终生成的会话 ID 永远以当前登录员工的 `empId` 作为强制前缀，这意味着即便员工 A 精确猜到或截获了员工 B 曾经使用过的子会话标识字符串，也无法用这个值拼出与员工 B 相同的完整会话 ID，从根本上杜绝了跨员工读取他人对话记忆的可能性。教师应引导学生把这一设计与单元 3 中学过的"越权访问防护"原则联系起来——地址簿、订单归属校验是"业务数据层面"的越权防护，会话隔离是"对话记忆层面"的越权防护，二者遵循同一套安全设计哲学："永远以服务端已认证的身份信息为唯一权威依据划定数据边界，任何客户端传入的标识符都只能在这个边界内部发挥作用，不能突破边界"。

第四层防御是**限流**。`AgentRateLimiter` 按员工维度实现固定窗口限流，默认每位员工每分钟最多发起 20 次对话请求，超过阈值的请求直接被拒绝并提示"操作过于频繁，请稍后再试"。限流的意义有两层：一是防止恶意或异常客户端（例如一个死循环脚本）无限制刷接口，耗尽调用大模型 API 所需的付费额度；二是限制单个用户对系统整体资源（Agent 线程池、数据库连接等）的占用比例，避免"一个人的异常行为拖垮所有人的正常使用体验"，这是多租户/多用户系统中资源公平分配的基本工程手段，教师可以借此简单介绍固定窗口、滑动窗口、令牌桶、漏桶四种主流限流算法的思路差异，并说明本项目选择实现最简单的固定窗口算法是因为当前场景对精度要求不高、优先保证实现简单可靠。

第五层防御是**有界线程池**。教师应重点对比"有界线程池"与"无界线程池"（如 `Executors.newCachedThreadPool()`）在高并发场景下的行为差异——无界线程池在任务提交速度持续超过任务处理速度时，会不断创建新线程来处理积压的任务，而线程本身是有内存开销的系统资源（每个线程默认会分配上百KB到几MB的栈空间），持续无限创建线程最终会耗尽服务器内存或者操作系统允许的最大线程数，导致整个应用（而不仅仅是 Agent 模块）崩溃；本项目 `AgentConfig` 中配置的线程池核心线程数为 4、最大线程数为 32、等待队列容量为 100，意味着当并发请求量超出这个处理能力上限时，新提交的任务会被 `ThreadPoolExecutor.AbortPolicy` 拒绝策略直接拒绝并抛出 `RejectedExecutionException`，`AgentController` 捕获这个异常后向前端返回一条"助手繁忙，请稍后再试"的友好提示，而不是让服务器资源被无限占用直至彻底宕机。教师应将这一设计原则总结为"宁可优雅地拒绝部分请求，也不能允许系统资源被无限占用直至整体崩溃"，这是所有高并发系统设计中必须具备的自我保护意识。

第六层防御是**系统提示词约束**。`@SystemMessage` 中明确写入了若干行为红线，例如禁止编造不存在的订单数据、遇到缺少必要参数的写操作请求时必须先追问用户而不能自行猜测填充、拒绝回答与本系统源码实现、密钥配置、微信支付密钥等高度敏感的技术内部信息相关的问题。教师应向学生说明，系统提示词层面的约束属于"软约束"，其可靠性依赖于大模型本身对指令的遵循能力，理论上存在被精心构造的"越狱提示词"绕过的可能性，因此系统提示词约束不能作为唯一的安全防线，必须与前述的二次确认、参数上限、限流、线程池隔离等"硬约束"（在代码逻辑层面强制生效、不依赖模型是否听话）配合使用，这是本单元最重要的一条设计哲学：**软约束负责提升体验和减少误判，硬约束负责兜底安全边界，二者不可互相替代**。

最后，教师应结合部署环节讲解 Nginx 在整个系统中承担的角色。生产环境中，前端构建产物由 Nginx 直接托管为静态资源，所有 `/api` 前缀的请求通过 `proxy_pass` 配置转发给后端 Spring Boot 应用并去除 `/api` 前缀，这与开发环境下前端 `vue.config.js` 中配置的开发代理规则（`pathRewrite`）在语义上完全对应，只是实现层面从"前端开发服务器的代理中间件"切换为"生产环境的反向代理服务器"，这种"开发环境代理规则与生产环境 Nginx 规则语义对齐"的设计，保证了前端代码本身不需要因为部署环境的切换而修改任何请求路径逻辑。SSE 长连接和 WebSocket 长连接在经过 Nginx 转发时都需要特别的配置项（例如 SSE 需要关闭响应缓冲 `proxy_buffering off`，WebSocket 需要正确处理 `Upgrade`/`Connection` 请求头完成协议升级转发），教师应结合 `/workspace/deploy/nginx` 目录下的实际配置文件，带学生逐条核对这些配置项存在的必要性。

**代码实操指引**：

要求学生完成：第一步，模拟对本地模式发起一句包含歧义的写操作请求（例如"我不想打烊"），观察系统是否正确识别为写意图并进入二次确认流程，而不是直接执行；第二步，编写一个简单的压测脚本（可以用 Shell 循环调用 curl），在短时间内对 Agent 接口发起超过限流阈值的请求次数，验证限流机制是否正确生效并返回预期的错误提示；第三步，人为将 `AgentConfig` 中的线程池参数临时调小（例如核心线程数改为 1、队列容量改为 2），配合并发压测观察 `RejectedExecutionException` 被触发和捕获的完整过程；第四步，阅读 `/workspace/deploy/nginx` 目录下的实际配置文件，找出针对 SSE 和 WebSocket 分别做了哪些特殊处理，并说明如果遗漏这些配置会分别出现什么故障现象。

**易错点/常见误区**：

学生常见的误区之一是把系统提示词约束当作唯一的安全保障，认为"只要在 Prompt 里写清楚规则，模型就一定会遵守"，教师必须结合"提示词注入""越狱攻击"等真实存在的大模型安全议题，让学生认识到软约束的天然脆弱性，进而理解为什么本项目要在代码逻辑层面叠加多层硬约束。误区之二是认为限流和有界线程池是"性能优化"手段，实际上二者的第一属性是"系统自我保护"手段，性能提升是附带收益而非设计初衷，混淆这两个定位会导致学生在设计限流阈值时只考虑吞吐量最大化而忽视了资源保护的本意。误区之三是在设计确认类交互时，把"确认"和"取消"的关键词判断写得过于简单粗暴（例如只匹配"确认"这一个词），忽视了自然语言表达的多样性，本项目 `isConfirm()`/`isAbort()` 方法各自匹配了一组同义表达，教师应提醒学生在设计类似交互时要充分考虑真实用户的表达习惯。

**面试真题**：

1. 一个具备写操作能力的 AI Agent 系统，相比单纯的问答机器人，需要额外考虑哪些安全风险？请至少列举四类并说明本项目对应的防御手段。答案要点：意图误判导致误执行写操作（二次确认机制）；参数异常/超大查询导致敏感数据泄露（参数硬上限）；跨会话越权读取他人对话记忆（会话 ID 强制绑定身份前缀）；恶意刷量耗尽资源或模型调用额度（按用户限流、有界线程池）。
2. 为什么系统提示词约束不能作为唯一的安全防线？答案要点：系统提示词是"软约束"，依赖模型本身对指令的遵循程度，存在被精心构造的提示词绕过的风险（提示词注入/越狱），必须配合代码逻辑层面不依赖模型行为的"硬约束"共同构成完整防线。
3. 有界线程池相比无界线程池的核心优势是什么？请结合本项目参数说明。答案要点：无界线程池在任务持续积压时会无限创建新线程，最终耗尽内存或系统线程资源导致整个应用崩溃；有界线程池（本项目核心 4、最大 32、队列 100）在超出处理能力时主动拒绝新任务并返回明确的错误提示，牺牲部分请求的可用性来保证系统整体的稳定性，这是一种"优雅降级"而非"全盘崩溃"的自我保护设计。
4. 请说明本项目会话隔离机制的具体实现方式，它防御的是哪一类攻击？答案要点：会话 ID 格式固定为 `emp:{empId}:{sub}`，`empId` 来自服务端验证过的登录身份而非客户端可控输入，客户端传入的 `sub` 只能在该员工身份范围内生效，防御的是"跨用户越权读取他人对话历史/记忆"这一类攻击。
5. 为什么 `searchOrders` 工具要对 `pageSize` 做硬编码上限，而不是信任模型传入的合理数值？答案要点：模型可能因为幻觉、被诱导或程序性错误传入异常大的数值，如果不做硬性拦截，会一次性查出大量包含顾客手机号等敏感信息的订单数据并回灌进模型上下文，这些数据随后会被发送到大模型服务商的服务器，构成实质性的隐私数据泄露，因此必须在代码层面做不依赖模型行为的强制限制。

**本单元产出**：学生提交一份 Agent 安全防线清单（至少覆盖二次确认、参数上限、会话隔离、限流、有界线程池五项，逐项说明防御目标和触发验证方式），以及一份 Nginx 部署配置的批注文档，标注出针对 SSE 和 WebSocket 的特殊配置项及其必要性。

# 四、面试专题突击

## 4.1 项目介绍模板

**30 秒版本**：本项目是苍穹外卖智能体改造版，一个面向餐饮行业的外卖管理系统，我主要负责后端开发，基于 Spring Boot 2.7、MyBatis、Redis、JWT 实现了菜品管理、订单全生命周期、微信支付、报表统计等核心功能，同时基于 LangChain4j 实现了一个 AI 老板助手模块，让管理员可以用自然语言查询经营数据、处理订单，这部分重点解决了 Function Calling 的工具调用设计和 Agent 系统的安全防护问题。

**3 分钟版本**：这个项目分为传统外卖管理后台和 AI 老板助手两大部分。传统后台部分，我实现了基于 JWT 和 Servlet 拦截器的鉴权体系，通过 ThreadLocal 在请求生命周期内传递用户身份；用 AOP 切面统一处理公共字段自动填充，避免每个新增/修改方法重复写样板代码；订单模块设计了完整的状态机，涵盖待付款、待接单、已接单、派送中、已完成、已取消六种状态，并且做了金额服务端重算防止价格篡改、支付回调幂等性处理防止重复推进状态；缓存方面用 Redis 存储店铺状态和菜品数据，管理端修改后主动清缓存保证一致性；实时通信方面用 WebSocket 做来单提醒的全局广播。AI 助手部分，基于 LangChain4j 的 `AiServices` 声明式编程，把订单查询、报表统计、店铺开关等业务能力包装成 `@Tool` 工具方法供大模型调用，重点解决了几个工程难题：一是 Skill 对象每次请求现场创建而不是做成单例 Bean，既能绑定请求级状态，又能保证内部调用的 Service 仍是被 AOP 增强的代理对象，事务和缓存不会被绕过；二是工具方法参数统一用字符串类型并做防呆解析，应对模型可能返回的异常参数；三是设计了完整的 Agent 安全防线，包括写操作二次确认、按会话隔离对话记忆、按用户限流、有界线程池防止资源耗尽、敏感查询结果做硬性数量上限，防止大模型无意间把大量用户隐私数据回灌进对话上下文造成泄露。整个项目让我对"如何在保证工程可靠性和安全性的前提下引入 AI 能力"有了比较系统的实践认知。

## 4.2 高频八股与项目结合

**ThreadLocal**：面试官常问"ThreadLocal 的实现原理及内存泄漏场景"，回答时必须结合项目落地——本项目 `BaseContext` 用一个 `ThreadLocal<Long>` 在拦截器 `preHandle` 中写入当前登录用户 ID，各层通过 `getCurrentId()` 读取而无需层层传参，`afterCompletion` 中调用 `removeCurrentId()` 清理；Agent 模块因为业务逻辑跑在独立线程池中，ThreadLocal 不能跨线程自动传递，所以在 `AbstractSkill.invoke()` 里手动 `setCurrentId`/`finally` 块中 `removeCurrentId`，这是对"ThreadLocal 绑定线程而非绑定请求"这一本质特性的具体应用与规避。

**AOP**：面试官常问"Spring AOP 和 AspectJ 的区别、AOP 的实现原理"，回答时结合 `AutoFillAspect` 说明——Spring AOP 是运行时基于动态代理（JDK 动态代理或 CGLIB）实现，只能拦截 Spring 容器管理的 Bean 之间的方法调用，本项目用它拦截 Mapper 层标注了 `@AutoFill` 注解的方法，在方法执行前通过反射调用实体对象的 setter 方法完成公共字段填充；AspectJ 是编译时或类加载时织入，功能更强大（可以拦截任意 Java 对象的方法调用，不限于 Spring Bean）但配置更复杂，本项目场景下 Spring AOP 已经完全够用，没有必要引入更重的 AspectJ 完整能力。

**MyBatis 缓存**：面试官常问"MyBatis 一级缓存和二级缓存的区别及使用注意事项"，本项目实际生产配置中通常关闭或谨慎使用 MyBatis 自带的二级缓存，转而使用 Redis 做业务层缓存（如店铺状态、菜品数据），原因是 MyBatis 二级缓存是基于 namespace 的粗粒度缓存，在多表关联、频繁更新的业务场景下极易出现脏读问题且难以精细控制失效范围，而业务层主动管理的 Redis 缓存可以精确控制缓存粒度（例如按分类 ID 缓存菜品）和精确的失效时机（管理端修改后立即清除对应键），可控性远胜于框架自带的缓存机制。

**JWT**：面试官常问"JWT 相比 Session 的优劣、JWT 如何实现注销"，本项目的回答要点是——JWT 无状态、适合分布式部署，但存在"签发后难以主动撤销"的固有缺陷，本项目通过管理端拦截器在验签之后额外查询数据库复核员工账号状态，实现了"账号被禁用即视为令牌失效"的准实时撤销能力，这是在不引入额外的令牌黑名单存储（如 Redis 维护已注销 Token 列表）的前提下，用较低成本解决"注销"这一 JWT 经典痛点的工程方案。

**Redis**：面试官常问"缓存穿透、缓存击穿、缓存雪崩的区别及解决方案"，本项目结合实际场景的回答是——店铺状态缓存采用永不过期策略从根本上避免了雪崩风险（因为它不会过期，也就不存在"大量 key 同时过期"的问题）；菜品缓存通过管理端主动清除而非依赖 TTL 自然失效来维持一致性，因此也不存在雪崩风险；对于缓存穿透（查询一个根本不存在的分类 ID），本项目未做专门的空值缓存或布隆过滤器处理，这是一个可以在面试中主动指出的"待改进点"，展示候选人具备批判性思考现有系统的能力而非简单复述。

**SSE vs WebSocket**：面试官常问"这两者的区别以及各自的适用场景"，本项目提供了教科书级的对比案例——AI 对话场景选 SSE，因为交互本质是"客户端发一次请求、服务端流式返回一段响应"的单向推送，且 SSE 基于普通 HTTP，能被标准反向代理无障碍转发，不需要处理协议升级的复杂性；来单提醒场景选 WebSocket，因为商家端需要在整个工作时段维持一条长期在线的连接以随时接收服务端主动推送的通知，属于典型的全双工长连接场景。回答这道题的关键是不要死记"SSE 单向、WebSocket 双向"这句结论，而要能结合本项目两个具体场景说明"为什么某个场景的通信语义决定了协议选型"。

**Agent 幻觉与工具调用的关系**：面试官常问"大模型幻觉问题在你的 Agent 项目里怎么应对"，本项目系统提示词明确要求模型"禁止编造数据，必须调用工具获取真实数据"，这是应对幻觉问题最直接有效的工程手段——让模型不再凭"记忆"或者"猜测"回答任何涉及真实业务数据的问题，而是强制通过 Function Calling 调用真实的后端接口获取权威数据后再组织语言回复，从架构设计的层面而不是单纯依赖模型能力的层面压低了幻觉发生的概率；对于模型可能在解析用户意图或者填充工具参数时出现的"参数级幻觉"（如编造一个不存在的订单 ID），本项目通过要求模型在缺少必要参数时先追问用户、以及 Skill 层对参数做防呆解析和业务校验兜底解决。

**Skill 层设计**：这是本项目区别于普通 Spring Boot CRUD 项目的最大亮点，面试官如果问到 Agent 相关经历，几乎必然会深挖这一部分。回答的核心逻辑链是：Skill 对象每请求 `new`（因为要绑定请求级状态：sink 和 empId）→ Skill 构造函数注入的 Service 依然是 Spring 管理的 AOP 代理对象（因此不绕过事务、缓存等横切逻辑）→ 工具方法参数统一用 String（因为模型输出不可信，需要业务代码自行防呆解析）→ 所有工具执行都经过统一的 `invoke()` 模板方法（负责发送 SSE 事件、绑定/清理 ThreadLocal、异常转中文提示、结果截断），这一整套设计体现了候选人不仅"会用" LangChain4j 的 API，更理解如何把一个新技术嵌入已有的、经过考验的工程体系中而不破坏原有的可靠性保障。

## 4.3 系统设计题

**多商户 SaaS 改造**：面试官可能会问"如果要把这个单商户外卖系统改造成支持多个商户入驻的 SaaS 平台，你会怎么设计？"这是一道考察系统设计能力的开放题，标准的回答思路应包含以下要点。首先是数据隔离方案的选择：可以采用"共享数据库、每张业务表新增 `merchant_id` 字段做行级隔离"的方案，改造成本较低，适合商户数量不算特别巨大且对隔离强度要求不是极端严苛的场景；也可以采用"每个商户独立数据库/独立 Schema"的方案，隔离性更强但运维复杂度和资源成本显著提高，需要结合实际商户规模和预算权衡选择。其次是现有鉴权体系的改造：JWT 的 Claims 中需要新增 `merchantId` 字段，`BaseContext` 需要同时存储 `empId` 和 `merchantId`，所有涉及数据查询和修改的 SQL 都必须补充 `merchant_id` 过滤条件，这一改造工作量巨大且极易遗漏，建议在 Mapper 层通过 MyBatis 插件（类似 PageHelper 的实现思路）统一自动拼接 `merchant_id` 条件，而不是要求开发者在每一条 SQL 里手动添加，从架构层面杜绝"忘记加商户过滤条件导致跨商户数据泄露"这一高危漏洞的可能性。再次是缓存 key 的改造：现有 Redis 缓存 key（如 `dish_{categoryId}`、`SHOP_STATUS`）都需要补充商户维度前缀（如 `merchant_{merchantId}_dish_{categoryId}`），否则不同商户的缓存数据会互相覆盖污染。最后是 Agent 模块的改造：会话隔离机制需要同时绑定商户和员工两个维度（`merchant:{merchantId}:emp:{empId}`），且每个商户可能需要独立配置自己的营业数据边界，Skill 层调用 Service 时传入的查询条件也必须自动带上当前商户 ID，防止 AI 助手跨商户查询或操作数据。

**Agent 限流降级**：面试官可能会问"如果大模型服务商的 API 出现大面积不可用或者响应严重延迟，你会如何设计降级方案？"标准回答应体现多级降级思路，而不是简单的"重试"。第一级降级是超时熔断：为每次模型调用设置合理的超时时间（本项目已经配置 `timeout-seconds`），超时后立即失败并向用户返回明确提示，而不是让用户长时间等待一个可能永远不会响应的请求，同时应该在服务端记录连续失败次数，一旦短时间内失败率超过某个阈值，主动触发"熔断"，在熔断窗口期内直接跳过对大模型 API 的实际调用，直接返回降级响应，避免持续把失败请求发送给已经不健康的下游服务，这是经典的熔断器模式（Circuit Breaker）思想。第二级降级是自动切换到本地规则模式：本项目本身已经具备"无 API Key 时走关键词匹配的本地模式"这一设计，可以进一步扩展为"检测到大模型服务连续异常时，自动临时切换到本地模式，恢复健康后再切回 LLM 模式"，让用户至少能继续使用最基本的查询和确认式操作能力，而不是整个 Agent 功能完全瘫痪。第三级降级是分级限流：在大模型服务出现容量紧张的信号时，可以临时下调每位用户的限流阈值（例如从每分钟 20 次降低到 5 次），用限流换取服务的持续可用性，而不是让少数活跃用户耗尽全部容量导致其他用户完全无法使用。第四级是给用户清晰、诚实的状态反馈：无论采用哪种降级策略，都应该让前端明确展示"当前处于降级模式"这一状态，而不是静默降级让用户以为系统出了未知故障，清晰的状态透明度本身也是良好系统设计的一部分。

# 五、教学评估方案

教学评估应贯穿单元教学的全过程，而不是仅在课程结束时进行一次性考核，本方案建议采用"过程性评估 + 阶段性评估 + 综合性评估"三级评估体系。

**过程性评估**（占总评估权重 40%）针对每一个教学单元展开，考核形式为"代码实操产出物 + 现场讲解"。每个单元结束后，学生需要提交该单元"本单元产出"部分要求的具体交付物（代码、测试报告、图纸等），并在课堂上用不超过 5 分钟的时间现场讲解自己的实现思路，教师根据讲解的准确性、对易错点的规避程度、代码的规范性三个维度打分。这一评估方式的价值在于及时发现学生在某个单元上的知识漏洞，避免"前面单元没学透、后面单元听不懂"的雪球效应——由于本方案的 8 个单元存在严格的前置依赖关系（见第二章的知识依赖图谱），任何一个单元的过程性评估不达标，都应该要求学生在进入下一单元前完成补救学习，而不是"先赶进度、后面再补"。

**阶段性评估**（占总评估权重 30%）建议在单元 4（订单全生命周期）和单元 8（Agent 安全与工程化）结束后各安排一次，形式为笔试加机试结合。笔试部分考核学生能否独立画出订单状态机图、能否准确列举 Agent 安全防线的完整清单等偏重"系统性理解"的内容；机试部分要求学生在限定时间内（建议 90 分钟）独立完成一个小型编码任务，例如"给现有系统新增一个具备状态机约束的业务模块"或者"为 Agent 模块新增一个具备参数防呆能力的 Skill 工具"，考核的不是代码量而是学生能否在压力环境下正确应用本方案强调的工程规范（分层、异常处理、参数校验、AOP 复用等）。

**综合性评估**（占总评估权重 30%）安排在全部 8 个单元教学结束后，采用"项目答辩"的形式，更贴近真实工程面试的考核方式。学生需要基于本项目完成一个完整的功能扩展（建议从"新增一种订单统计维度""为管理后台新增一个业务模块并同步接入 Agent 查询能力""设计并实现一种新的缓存策略"等题目中选择，也可以结合第四章"系统设计题"部分自选一道设计题目并给出详细方案），并在答辩环节接受教师和同学的提问，问题应覆盖本方案第四章列出的高频八股题目，重点考核学生能否做到"讲原理不空洞、结合代码不生搬硬套"，即真正达到"教科书式严谨"这一培养目标所要求的认知深度。

评估结果的反馈方式建议采用"问题清单 + 补救学习路径"而非单纯的分数,对于过程性评估中反复出现同类问题的学生（例如反复混淆 `#{}` 与 `${}`、反复遗漏 ThreadLocal 清理），教师应在评估反馈中明确指出该知识点在依赖图谱中的位置及其影响范围，引导学生认识到"这不是一个孤立的小失误，而是会连锁影响后续单元学习效果的关键地基",并给出具体的补救学习步骤（重新阅读哪一段代码、重新完成哪一项实操）,而不是仅仅告知"这道题扣了多少分"这种缺乏建设性的反馈方式。教学评估的最终目标不是筛选和淘汰,而是通过持续、具体、可执行的反馈,确保每一位学生都能扎实达成本方案第一章设定的知识、能力、素养三维教学目标。
