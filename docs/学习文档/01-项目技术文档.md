# 一、项目概述与技术栈总览

## 1.1 项目定位

苍穹外卖（sky-take-out-agent）是一个面向餐饮行业的外卖管理系统，核心由两大产品形态组成：其一是传统的外卖商家管理后台，覆盖员工管理、菜品管理、套餐管理、订单处理、数据报表等全链路经营功能；其二是创新性的 AI 老板助手模块，管理员可通过自然语言对话完成查询营业数据、处理订单、开关店铺等高频操作，后端基于 LangChain4j 框架实现 Agent 能力，前端以 SSE 流式对话的方式呈现。系统整体分为 C 端微信小程序（用户下单、支付、查看订单）和 B 端管理后台（Vue2 单页应用），后端统一使用 Spring Boot 2.7.3 提供 RESTful API 服务，通过 Nginx 反向代理实现前后端分离部署。

## 1.2 三模块职责

项目采用 Maven 多模块结构，父工程 `sky-take-out` 下辖三个子模块，各自职责明确、依赖清晰：

| 模块名 | artifactId | 职责说明 |
|--------|-----------|---------|
| sky-common | sky-common | 基础设施层：存放全局常量（`StatusConstant`、`MessageConstant`）、ThreadLocal 上下文（`BaseContext`）、工具类（`JwtUtil`、`AliOssUtil`、`HttpClientUtil`、`WeChatPayUtil`）、配置属性类（`JwtProperties`、`AliOssProperties`、`WeChatProperties`）、统一返回结构（`Result`、`PageResult`）、自定义异常体系（`BaseException` 及其子类）、Jackson 序列化定制（`JacksonObjectMapper`）。该模块不含任何业务逻辑，被另外两个模块依赖。 |
| sky-pojo | sky-pojo | 数据对象层：存放所有 Entity（数据库表映射）、DTO（前端请求参数）、VO（响应视图对象），各对象通过 Lombok `@Data`/`@Builder` 生成样板代码，通过 `@Schema` 注解补充 OpenAPI 文档说明。该模块仅依赖 Lombok、Jackson、Swagger Annotations 和 Spring Context（`@DateTimeFormat`），不引入 Web 或持久层依赖，保持极度轻量。 |
| sky-server | sky-server | 主服务模块：包含 Controller（表现层）、Service（业务层）、Mapper（持久层）、Interceptor（拦截器）、Config（配置类）、AOP 切面、WebSocket、定时任务以及整个 Agent 子系统（controller、service、skill、memory、sse、config、dto），是唯一可独立运行的 Spring Boot 应用，打包为可执行 JAR。 |

## 1.4 Agent 框架选型：LangChain4j 0.35.0

本项目的 AI Agent 模块选择 LangChain4j 而非 Spring AI 或直接调用 HTTP API，基于以下技术考量：第一，LangChain4j 提供声明式 `AiServices` 接口，只需定义一个 Java Interface 并标注 `@SystemMessage`，即可自动获得带对话记忆、工具调用、流式输出的完整 Agent，开发效率远高于手动拼接 Prompt 和解析 Function Call JSON；第二，`@Tool` 注解允许将普通 Java 方法注册为模型可调用的函数，框架自动生成 JSON Schema 描述、解析模型返回的 tool_calls、执行方法并将结果回灌模型，开发者无需手写任何 Function Calling 协议代码；第三，0.35.0 是 LangChain4j 最后一个编译目标为 Java 8 字节码的版本（0.36.0 起最低要求 JDK 17），而本项目基于 Spring Boot 2.7.3，编译级别为 1.8，因此 0.35.0 是唯一可用的版本上限。

## 2.2 逐层技术说明

**Interceptor 层**：在 `WebMvcConfiguration` 中注册两个拦截器，`JwtTokenAdminInterceptor` 拦截 `/admin/**`（排除登录接口），`JwtTokenUserInterceptor` 拦截 `/user/**`（排除登录和店铺状态查询）。拦截器在 `preHandle` 中解析 JWT、提取用户 ID 存入 `BaseContext`（ThreadLocal），在 `afterCompletion` 中清理 ThreadLocal 防止内存泄漏。管理端拦截器额外增加了账号状态复核——从数据库查询员工当前状态，被禁用的员工即使持有未过期令牌也会被拒绝访问。

**Controller 层**：按用户角色划分为 `admin`（管理端）、`user`（C 端用户）、`notify`（支付回调）、`agent`（AI 助手）四个包。所有 Controller 使用 `@RestController` 注解，返回值统一封装为 `Result<T>` 对象（code=1 成功 / code=0 失败），分页接口返回 `Result<PageResult>`。各 Controller 只做参数接收、日志记录和调用 Service，不包含业务逻辑。

**Service 层**：每个业务领域对应一个 Service 接口和 Impl 实现类。实现类使用 `@Service` 注解注册为 Spring Bean，涉及多表操作的方法（如新增菜品含口味、用户下单）通过 `@Transactional` 保证事务一致性。核心业务逻辑包括订单状态机校验、金额服务端重算、密码哈希升级、配送范围校验等。

**Mapper 层**：采用 MyBatis XML 映射文件方式编写 SQL，Mapper 接口用 `@Mapper` 注解标记。动态 SQL 大量使用 `<if>`、`<where>`、`<set>`、`<foreach>` 标签，实现条件查询、动态更新、批量插入等灵活操作。`application.yml` 中配置 `map-underscore-to-camel-case: true` 实现数据库下划线到 Java 驼峰的自动映射。

**Agent 层**：独立的 `com.sky.agent` 包，包含 controller、service、skill、memory、sse、config、dto 七个子包。Agent 不直接操作数据库，而是通过调用已有的 Service 层方法来执行业务操作，保证了 AOP（事务、缓存）不被绕过。

# 三、数据结构与数据库设计

## 3.1 数据库表结构与 ER 关系

系统共包含 11 张核心数据表，按业务领域可分为用户域、商品域、订单域三组，彼此通过外键或逻辑关联形成完整的数据模型。

**用户域**：`employee`（员工表）存储管理端操作人员信息，`user`（用户表）存储 C 端微信用户信息，`address_book`（地址簿）存储用户的收货地址，通过 `user_id` 与 `user` 表关联。

**商品域**：`category`（分类表）存储菜品分类和套餐分类（type=1 菜品/type=2 套餐），`dish`（菜品表）通过 `category_id` 关联分类，`dish_flavor`（口味表）通过 `dish_id` 关联菜品（一对多），`setmeal`（套餐表）通过 `category_id` 关联分类，`setmeal_dish`（套餐菜品关系表）是 `setmeal` 与 `dish` 的多对多中间表。

**订单域**：`shopping_cart`（购物车表）通过 `user_id` 关联用户，通过 `dish_id` 或 `setmeal_id` 关联商品，`orders`（订单主表）通过 `user_id` 关联用户、通过 `address_book_id` 关联地址，`order_detail`（订单明细表）通过 `order_id` 关联订单主表（一对多）。

ER 关系摘要：`user` 1:N `address_book`；`user` 1:N `shopping_cart`；`user` 1:N `orders`；`orders` 1:N `order_detail`；`category` 1:N `dish`；`category` 1:N `setmeal`；`dish` 1:N `dish_flavor`；`setmeal` M:N `dish`（通过 `setmeal_dish`）；`employee` 独立，仅在 `create_user`/`update_user` 字段中被引用。

## 3.2 Entity / DTO / VO 三层数据对象

在 Spring Boot 项目中，为了实现关注点分离和安全性控制，数据对象通常被分为三种类型，各自承担不同的职责。Entity 是数据库表的一对一映射对象，字段与表列严格对应，包含所有列（含密码等敏感字段），用于 Mapper 层与数据库交互，典型如 `Employee` 实体包含 `password`、`idNumber` 等字段。DTO（Data Transfer Object）是前端向后端传递请求参数的载体，只包含本次操作所需的字段，例如 `EmployeeLoginDTO` 只有 `username` 和 `password`，`OrdersSubmitDTO` 只有下单所需的地址 ID、配送方式等，不含 `userId`（由服务端从 ThreadLocal 获取，防止客户端伪造）。VO（View Object）是后端向前端返回数据的视图对象，按展示需要裁剪和聚合字段，例如 `EmployeeVO` 不含 `password` 字段避免密码泄露，`EmployeeLoginVO` 聚合了 `id`、`userName`、`name`、`token`，`OrderVO` 在 `Orders` 基础上增加了 `orderDetailList` 和 `orderDishes` 字段。Entity、DTO、VO 之间通过 `BeanUtils.copyProperties()` 进行属性拷贝，在 Service 层完成转换。

## 3.3 核心实体字段说明

### Orders（订单实体）

Orders 实体包含完整的订单状态机，通过 6 个静态常量定义状态流转：`PENDING_PAYMENT(1)` 待付款 → `TO_BE_CONFIRMED(2)` 待接单 → `CONFIRMED(3)` 已接单 → `DELIVERY_IN_PROGRESS(4)` 派送中 → `COMPLETED(5)` 已完成；任何非终态均可转为 `CANCELLED(6)` 已取消。支付状态独立维护三个值：`UN_PAID(0)` 未支付、`PAID(1)` 已支付、`REFUND(2)` 退款。核心字段包括 `number`（订单号，时间戳+4位随机数）、`status`（订单状态 1-6）、`userId`（下单用户）、`amount`（BigDecimal 实收金额）、`phone`（收货手机号）、`address`（收货地址）、`consignee`（收货人）、`cancelReason`/`rejectionReason`（取消/拒单原因）、`orderTime`/`checkoutTime`/`deliveryTime`/`cancelTime`（时间节点）、`packAmount`（打包费）。

### Employee（员工实体）

员工实体映射 `employee` 表，包含 `id`、`username`（登录账号）、`name`（姓名）、`password`（密码，BCrypt 哈希存储）、`phone`（手机号）、`sex`（性别）、`idNumber`（身份证号）、`status`（0 禁用/1 启用）及四个公共字段 `createTime`/`updateTime`/`createUser`/`updateUser`。密码存储经历了明文→MD5→BCrypt 的演进，登录时 `matchesAndUpgradePassword` 方法兼容三种格式并自动升级为 BCrypt。

### User（C端用户实体）

用户实体映射 `user` 表，以微信 `openid` 为唯一标识，包含 `name`、`phone`、`sex`、`idNumber`、`avatar`（头像 URL）、`createTime`。微信登录时若 openid 不存在则自动注册（插入一条新记录），实现静默登录。

### ShoppingCart（购物车实体）

购物车实体映射 `shopping_cart` 表，每条记录代表一项商品，通过 `userId` 绑定用户，`dishId` 或 `setmealId`（二选一）指向具体菜品或套餐，`dishFlavor` 记录所选口味，`number` 记录数量，`amount` 记录单价（加购时从菜品/套餐表写入，非客户端传入），`name`/`image` 冗余存储以加速展示。

### AddressBook（地址簿实体）

地址簿映射 `address_book` 表，包含 `userId`（归属用户）、`consignee`（收货人）、`phone`（手机号）、三级行政区划（`provinceName`/`cityName`/`districtName`）、`detail`（详细地址）、`label`（标签如"家"/"公司"）、`isDefault`（0 否/1 是默认地址）。所有增删改查操作均通过 `getOwnedAddress` 方法校验归属权，防止越权访问他人地址。

# 四、全业务数据流转详解

## 4.1 员工登录 + JWT 签发 + 鉴权拦截

前端请求：`POST /api/employee/login`，Body 为 `{ username, password }`。Nginx 将 `/api` 前缀改写为 `/admin`，实际到达 `POST /admin/employee/login`。该路径在 `WebMvcConfiguration` 中被排除拦截（`excludePathPatterns("/admin/employee/login")`），不经过 JWT 校验。`EmployeeController.login()` 接收 `@RequestBody EmployeeLoginDTO`，调用 `EmployeeServiceImpl.login()`。Service 层通过 `employeeMapper.getByUsername(username)` 查询员工记录（对应 `EmployeeMapper.xml` 中 `select * from employee where username = #{username}`），然后调用 `matchesAndUpgradePassword()` 进行密码校验——该方法兼容 BCrypt（`$2a$` 开头）、MD5、明文三种格式，匹配成功后将旧格式自动升级为 BCrypt 并回写数据库。密码正确后检查 `status` 是否为禁用状态。全部通过后，Controller 用 `JwtUtil.createJWT()` 以 HS256 算法签发 JWT，Claims 中写入 `empId`，TTL 从配置读取（默认 7200000 毫秒即 2 小时），组装 `EmployeeLoginVO`（含 id、userName、name、token）返回 `Result.success(employeeLoginVO)`。前端收到 token 后存入 Cookie，后续所有请求在 header 中携带 `token: <jwt>`。访问 `/admin/**` 其他接口时，`JwtTokenAdminInterceptor.preHandle()` 从 `request.getHeader("token")` 取出令牌，`JwtUtil.parseJWT()` 验签并提取 `empId`，再查库确认员工未被禁用，最后 `BaseContext.setCurrentId(empId)` 存入 ThreadLocal，`afterCompletion()` 中执行 `BaseContext.removeCurrentId()` 清理。

## 4.2 菜品/套餐 CRUD（含图片上传 OSS、分类关联、缓存）

以新增菜品为例：前端先通过 `POST /api/common/upload`（改写后 `/admin/common/upload`）上传图片文件。`CommonController.upload()` 接收 `MultipartFile file`，校验文件大小（不超过 `sky.upload.max-size-bytes` 默认 5MB）和扩展名（白名单 jpg/jpeg/png/gif/webp），通过后用 `UUID.randomUUID()` 生成唯一文件名，调用 `AliOssUtil.upload(bytes, objectName)` 上传至阿里云 OSS，返回图片 URL。随后前端发送 `POST /api/dish`（改写后 `/admin/dish`），Body 为 `DishDTO`（含 name、categoryId、price、image URL、description、flavors 列表）。`DishController.save()` 调用 `DishServiceImpl.saveWithFlavor()`，该方法使用 `@Transactional` 保证事务：先 `dishMapper.insert(dish)` 插入菜品主表（XML 中 `useGeneratedKeys="true" keyProperty="id"` 回填自增 ID），再遍历 flavors 列表设置 `dishId`，批量 `dishFlavorMapper.insertBatch(flavors)` 插入口味表。插入完成后，Controller 调用 `clearCache("dish_" + categoryId)` 清理对应分类的 Redis 缓存（使用 SCAN 命令替代 KEYS 避免阻塞 Redis）。C 端查询菜品时，`DishController(user)` 中用 `@Cacheable` 注解从 Redis 取缓存，缓存未命中才查库。

## 4.3 C 端用户微信登录

前端请求：`POST /user/user/login`，Body 为 `{ code }`（微信小程序 `wx.login()` 获取的临时授权码）。该路径被 User 拦截器排除，不做 JWT 校验。`UserController.login()` 调用 `UserServiceImpl.wxLogin()`，Service 内部调用 `getOpenid(code)` 方法——通过 `HttpClientUtil.doGet("https://api.weixin.qq.com/sns/jscode2session", params)` 向微信服务器换取用户 `openid`。拿到 openid 后，`userMapper.getByOpenId(openid)` 查询是否已注册，若为 null 则自动创建用户（`User.builder().openid(openid).createTime(LocalDateTime.now()).build()`）并 `userMapper.insert(user)` 插入数据库。最后 Controller 用 `JwtUtil.createJWT()` 签发用户端 JWT（Claims 中写入 `userId`，密钥和 TTL 与管理端独立），返回 `UserLoginVO`（含 id、openid、token）。

## 4.4 购物车加减

添加购物车：`POST /user/shoppingCart/add`，Body 为 `ShoppingCartDTO`（含 dishId 或 setmealId、dishFlavor）。`ShoppingCartController` 调用 `ShoppingCartServiceImpl.addShoppingCart()`。Service 先从 ThreadLocal 获取 `userId` 设置到查询条件中（只能操作自己的购物车），调用 `shoppingCartMapper.list(shoppingCart)` 查询是否已存在相同商品。若存在则 `number + 1` 并 `updateNumberById`；若不存在则根据 `dishId`/`setmealId` 分别从 `dishMapper.getById()` 或 `setmealMapper.getById()` 获取商品名称、图片、价格（注意价格由服务端从数据库取出，不信任客户端），然后 `shoppingCartMapper.insert()` 插入新记录。减少购物车：`POST /user/shoppingCart/sub`，逻辑类似，`number == 1` 时直接删除记录，否则 `number - 1` 并更新。

## 4.5 用户下单（金额重算、配送范围校验、订单号生成）

前端请求：`POST /user/order/submit`，Body 为 `OrdersSubmitDTO`（含 addressBookId、payMethod、remark、estimatedDeliveryTime 等）。`OrderController(user)` 调用 `OrderServiceImpl.submitOrder()`（标注 `@Transactional`）。Service 完整流程如下：首先从 ThreadLocal 取 `currentId`，通过 `addressBookMapper.getById()` 查询地址并校验归属权（`currentId.equals(addressBook.getUserId())`），防止用户使用他人地址下单。接着调用 `checkOutOfRange()` 校验配送范围——通过百度地图 Geocoding API 将店铺地址和用户地址分别解析为经纬度坐标，再通过路线规划 API 计算驾车距离，超过 5000 米则拒绝下单（未配置百度 AK 时跳过该校验）。然后查询当前用户购物车数据，为空则抛出异常。构建 `Orders` 对象，关键步骤是**金额服务端重算**：`calculateOrderAmount()` 方法遍历购物车每项的 `amount × number` 求和再加上打包费，结果写入 `order.setAmount()`，完全忽略客户端可能传入的金额字段，从根本上防止价格篡改。订单号通过 `generateOrderNumber()` 生成（`System.currentTimeMillis()` + 4 位随机数），状态设为 `PENDING_PAYMENT(1)`，支付状态设为 `UN_PAID(0)`。`orderMapper.insert(order)` 插入订单主表（`useGeneratedKeys` 回填 ID），遍历购物车构建 `OrderDetail` 列表并 `orderDetailMapper.insertBatch()` 批量插入明细表，最后 `shoppingCartMapper.deleteByUserId()` 清空购物车。返回 `OrderSubmitVO`。

## 4.6 微信支付 + 回调

用户端发起支付：`PUT /user/order/payment`，Body 为 `OrdersPaymentDTO`（含 orderNumber、payMethod）。`OrderServiceImpl.payment()` 通过 `orderMapper.getByNumberAndUserId()` 查询订单，调用 `weChatPayUtil.pay()` 向微信支付 API 提交预付单，返回 `OrderPaymentVO`（含 prepay_id 等前端唤起支付所需参数）。用户在小程序中完成支付后，微信服务器回调 `POST /notify/paySuccess`。`PayNotifyController.paySuccessNotify()` 从 request body 读取加密报文，使用 `AesUtil`（APIv3 密钥）解密得到明文 JSON，提取 `out_trade_no`（商户订单号）。调用 `orderService.paySuccess(outTradeNo)`：先查订单、幂等判断（已支付直接返回）、状态校验（仅 PENDING_PAYMENT 可转）、更新状态为 `TO_BE_CONFIRMED(2)` + `payStatus = PAID(1)` + `checkoutTime`，然后通过 `webSocketServer.sendToAllClient()` 向所有已连接的商家端推送来单消息（`{type:1, orderId, content}`）。最后向微信响应 `{code:"SUCCESS", message:"SUCCESS"}`。

## 4.7 商家接单/拒单/派送/完成（状态机转换）

接单：`PUT /admin/order/confirm`，Body 为 `OrdersConfirmDTO`（含 id）。`OrderServiceImpl.confirm()` 先查库校验订单存在且 `status == TO_BE_CONFIRMED(2)`，然后更新 `status = CONFIRMED(3)`。拒单：`PUT /admin/order/rejection`，Body 为 `OrdersRejectionDTO`（含 id、rejectionReason）。校验状态为 `TO_BE_CONFIRMED(2)`，若 `payStatus == PAID` 则调用 `weChatPayUtil.refund()` 发起退款，更新 `status = CANCELLED(6)`、`rejectionReason`、`cancelTime`。取消：`PUT /admin/order/cancel`，Body 为 `OrdersCancelDTO`，校验订单存在且非终态（非已完成/已取消），必须填写取消原因，已支付则退款，更新状态为 `CANCELLED(6)`。派送：`PUT /admin/order/delivery/{id}`，校验 `status == CONFIRMED(3)`，更新 `status = DELIVERY_IN_PROGRESS(4)`。完成：`PUT /admin/order/complete/{id}`，校验 `status == DELIVERY_IN_PROGRESS(4)`，更新 `status = COMPLETED(5)` 并设 `deliveryTime`。定时任务 `OrderTask` 补充处理两种异常情况：每分钟扫描超过 15 分钟未支付的订单自动取消；每天凌晨 1 点将超过 60 分钟仍为派送中的订单自动完成。

## 4.8 来单提醒（WebSocket 广播）

`WebSocketServer` 使用 `@ServerEndpoint("/ws/{sid}")` 声明 WebSocket 端点，前端管理页面在加载时通过 `new WebSocket("ws://host:8080/ws/{sid}")` 建立长连接。`@OnOpen` 方法将 `Session` 存入 `sessionMap`（以 sid 为 key），`@OnClose` 时移除。`sendToAllClient(String message)` 方法遍历所有 Session 调用 `session.getBasicRemote().sendText(message)` 实现广播。消息格式为 JSON：`type=1` 表示新订单通知，`type=2` 表示用户催单。前端收到 WebSocket 消息后弹窗提醒并播放提示音。

## 4.9 报表（营业额/用户/订单/Top10）+ Excel 导出

管理端报表接口统一在 `ReportController` 中，前端通过 `GET /admin/report/turnoverStatistics?begin=&end=` 等接口查询。以营业额报表为例：`ReportServiceImpl.getTurnover()` 接收起止日期，生成日期列表，遍历每天调用 `orderMapper.sumByMap()` 统计当天已完成订单的金额总和（XML 中使用 `<where>` + `<if>` 动态条件），将日期列表和金额列表用逗号拼接后返回 `TurnoverReportVO`。用户统计调用 `userMapper.countByMap()` 分别统计每天新增用户和累计用户。订单统计分别统计每天总单量和有效（已完成）单量，计算完成率。销量 Top10 通过 `orderMapper.getSalesTop10()` 执行联表查询 `order_detail JOIN orders`，按商品名分组求 sum、降序取前 10。Excel 导出通过 `GET /admin/report/export`，`ReportServiceImpl.exportBusinessData()` 读取 `resources/template/运营数据报表模板.xlsx` 模板，使用 Apache POI 的 `XSSFWorkbook` 填充近 30 天的营业数据到对应单元格，通过 `response.getOutputStream()` 输出给浏览器下载。

## 4.10 AI 助手对话链路

完整链路：前端 `POST /api/agent/stream`（请求头 `token: <jwt>`、`Content-Type: application/json`、`Accept: text/event-stream`）→ Nginx 改写为 `/admin/agent/stream` → `JwtTokenAdminInterceptor` 验证 JWT 并将 empId 存入 BaseContext → `AgentController.stream()` 接收 `AgentChatRequest`（含 message 和可选 conversationId），创建 `SseEmitter`（超时 180 秒）和 `AgentEventSink`（封装 SSE 写入），从 BaseContext 取出 empId → 提交到 `agentExecutor`（有界线程池，4-32 线程，队列 100）异步执行 → `AgentChatService.chat()` 校验输入长度（≤2000 字）、限流（每员工每分钟 20 次）、生成会话 ID（`emp:{empId}:{sub}`，强绑定员工防止跨会话读取）。

**有 API Key 路径（LLM 模式）**：每请求 `new` 四个 Skill 实例（`OrderSkill`、`ReportSkill`、`WorkspaceSkill`、`ShopSkill`），传入 Spring 管理的 Service 代理对象、sink、empId。通过 `AiServices.builder(AgentAssistant.class).streamingChatLanguageModel(model()).chatMemoryProvider(...).tools(skills).build()` 装配 Agent。`AgentAssistant` 接口的 `@SystemMessage` 定义系统提示词（禁止编造数据、必须调用工具、不回答敏感问题等 6 条规则）。调用 `assistant.chat(conversationId, message)` 返回 `TokenStream`，注册 `onNext`（`sink.text(token)`）、`onComplete`（`sink.end()`）、`onError`（`sink.error(msg)`）回调，`start()` 启动流式输出。当模型决定调用工具时，LangChain4j 框架自动调用对应 Skill 的 `@Tool` 方法，Skill 内部通过 `invoke()` 模板方法发送 `tool_call` 事件 → 设置 BaseContext → 调用 Service 方法 → 异常转中文 → 截断（2000 字）→ 发送 `tool_result` 事件，结果回灌模型继续生成。

**无 API Key 路径（本地模式）**：`localChat()` 方法通过关键词匹配解析用户意图。读操作（营业额、店铺状态、订单总览、查订单）直接调用 Service 并通过 `invokeLocalRead()` 发送 `tool_call`/`tool_result` 事件。写操作（接单、拒单、取消、派送、完成、开关店）采用二次确认机制——`prepareWriteConfirmation()` 解析意图并在 `AgentPendingActionStore` 中登记待确认动作（含 toolName、args、action 闭包，TTL 120 秒），返回确认追问；用户回复"确认"时 `executePending()` 取出闭包执行；回复"取消"则清除。

前端 SSE 处理：`src/api/agent.ts` 中 `startAgentStream()` 使用原生 `fetch` API 发送 POST 请求，读取 `response.body` 的 `ReadableStream`，通过 `TextDecoder` 解码 UTF-8 文本，按 SSE 协议（`\n\n` 分隔事件块、`data:` 前缀）解析，`dispatchEvent()` 根据 JSON 中 `type` 字段分发五种事件：`text`（追加文本）、`tool_call`（展示工具调用卡片）、`tool_result`（填充执行结果）、`end`（结束流）、`error`（显示错误）。`src/views/agent/index.vue` 中的 `Agent` 组件维护 `messages` 数组，每条消息包含 `role`（user/assistant）、`content`、`tools`（ToolCard 数组）、`streaming` 标志，实时渲染对话气泡和工具调用卡片。

# 五、关键技术点深度解析

## 5.1 ThreadLocal（BaseContext 跨层传递登录态）

**原理**：ThreadLocal 是 JDK 提供的线程局部变量工具，每个线程持有一份独立的变量副本，互不干扰。其底层实现是在每个 Thread 对象内部维护一个 `ThreadLocalMap`，以 ThreadLocal 实例为 key、以存储值为 value。读写操作只访问当前线程的 Map，因此天然线程安全，无需加锁。

**本项目用法**：`BaseContext` 类封装了一个 `ThreadLocal<Long>` 静态变量，提供 `setCurrentId(Long id)`、`getCurrentId()`、`removeCurrentId()` 三个静态方法。在请求处理链路中，拦截器（`JwtTokenAdminInterceptor` / `JwtTokenUserInterceptor`）的 `preHandle` 阶段从 JWT 中提取用户 ID 并调用 `setCurrentId()`，之后 Controller、Service、Mapper 各层均可通过 `BaseContext.getCurrentId()` 获取当前登录用户 ID，无需在方法签名中层层传递。请求结束时，拦截器的 `afterCompletion` 调用 `removeCurrentId()` 清理 ThreadLocal，防止线程复用时数据串联（Tomcat 线程池中线程是复用的，不清理会导致下一个请求读到上一个用户的 ID）。Agent 模块中，由于 LLM 调用在独立线程池（agentExecutor）中执行，ThreadLocal 无法自动传递，因此 Skill 的 `invoke()` 方法在执行前手动 `BaseContext.setCurrentId(empId)`，执行后在 `finally` 块中 `removeCurrentId()`。

**面试高频问法**：ThreadLocal 会不会内存泄漏？答案是如果不调用 `remove()`，在线程池场景下 value 会随线程存活而无法被 GC 回收。本项目在拦截器的 `afterCompletion` 和 Skill 的 `finally` 块中均调用了 `removeCurrentId()` 来规避此风险。ThreadLocal 与 InheritableThreadLocal 的区别？后者支持父线程向子线程传递值，但在线程池中无效（线程已创建），本项目选择手动设置而非依赖继承。

## 5.2 AOP + 自定义注解（AutoFillAspect 自动填充公共字段）

**原理**：AOP（面向切面编程）通过动态代理在不修改目标代码的前提下，对方法执行前后织入横切逻辑。Spring AOP 默认使用 JDK 动态代理（接口）或 CGLIB（类）生成代理对象，在运行时拦截方法调用。`@Aspect` 标记切面类，`@Pointcut` 定义切入点表达式，`@Before`/`@After`/`@Around` 定义通知类型。

**本项目用法**：`AutoFill` 是自定义注解，声明在 `@Target(ElementType.METHOD)` 和 `@Retention(RetentionPolicy.RUNTIME)` 上，接受一个 `OperationType value()` 参数（枚举值 INSERT 或 UPDATE）。Mapper 接口中需要自动填充公共字段的方法上标注 `@AutoFill(OperationType.INSERT)` 或 `@AutoFill(OperationType.UPDATE)`。`AutoFillAspect` 的切入点表达式为 `execution(* com.sky.mapper.*.*(..)) && @annotation(com.sky.annotation.AutoFill)`，即仅拦截 Mapper 层中标注了该注解的方法。`@Before` 前置通知中，通过 `JoinPoint` 获取方法签名和参数，从注解中读取操作类型，然后通过**反射**调用实体对象的 `setCreateTime`/`setCreateUser`/`setUpdateTime`/`setUpdateUser` 方法，将 `LocalDateTime.now()` 和 `BaseContext.getCurrentId()` 填入。INSERT 操作填充 4 个字段，UPDATE 操作只填充 updateTime 和 updateUser，实现了公共字段赋值逻辑的集中管理，避免在每个 Service 方法中重复编写。

**面试高频问法**：Spring AOP 和 AspectJ 的区别？Spring AOP 是运行时代理，只能拦截 Spring 管理的 Bean 的方法调用；AspectJ 是编译时/加载时织入，功能更强但配置复杂。为什么不用 MyBatis 拦截器实现？MyBatis 拦截器更底层，且参数解析复杂，AOP 方案更直观、可维护性更强。

## 5.3 MyBatis 动态 SQL

**原理**：MyBatis 在 XML 映射文件中提供一组 OGNL 表达式驱动的标签，在 SQL 执行前根据参数条件动态拼接 SQL 片段。`<if test="条件">` 标签仅当条件为 true 时才拼接内部 SQL；`<where>` 标签自动添加 WHERE 关键字并去除开头多余的 AND/OR；`<set>` 标签用于 UPDATE 语句，自动添加 SET 关键字并去除末尾多余的逗号；`<foreach>` 标签遍历集合生成 IN 子句或批量 INSERT 的 VALUES 列表。

**本项目用法**：`OrderMapper.xml` 中的 `pageQuery` 是典型动态查询，通过 `<where>` 包裹多个 `<if>` 条件（number、phone、userId、status、beginTime、endTime），任意组合实现灵活过滤。`EmployeeMapper.xml` 中的 `update` 方法使用 `<set>` 包裹多个 `<if>` 字段，仅更新非 null 的字段，实现部分更新而不覆盖其他列。`DishMapper.xml` 中的分页查询使用 LEFT JOIN 关联分类表，并通过 `<if>` 按名称、分类 ID、状态动态过滤。`OrderMapper.xml` 中的 `sumByMap` 和 `countByMap` 通过 `<if test="status != null">` 和 `<if test="begin != null">` 实现按状态和时间区间的灵活统计。`getSalesTop10` 使用 `order_detail` 与 `orders` 联表查询，按 `o.status = 5`（已完成）过滤，`GROUP BY name ORDER BY number DESC LIMIT 10` 取销量前十。

**面试高频问法**：`${}` 和 `#{}` 的区别？`#{}` 使用 PreparedStatement 预编译参数，防 SQL 注入；`${}` 直接拼接字符串，存在注入风险，仅用于动态表名/列名等无法参数化的场景。本项目全部使用 `#{}` 参数绑定。

## 5.4 PageHelper 分页原理

**原理**：PageHelper 是 MyBatis 的分页插件，基于 MyBatis 的 `Interceptor`（拦截器）机制实现。其核心工作流程是：调用 `PageHelper.startPage(pageNum, pageSize)` 时，将分页参数存入 ThreadLocal；当下一条 MyBatis 查询执行时，PageHelper 的拦截器在 SQL 执行前从 ThreadLocal 读取分页参数，自动在原 SQL 末尾追加 `LIMIT offset, size`（MySQL 方言），同时先执行一条 `SELECT COUNT(*)` 统计总记录数；查询结果被封装为 `Page<T>` 对象（继承自 ArrayList），包含 `total`（总数）和 `result`（当前页数据）。查询完成后 ThreadLocal 被清理，避免影响后续查询。

**本项目用法**：在所有需要分页的 Service 方法中，调用模式统一为 `PageHelper.startPage(dto.getPage(), dto.getPageSize())`，紧接着调用 Mapper 的查询方法，返回 `Page<T>`，然后从中提取 `total` 和 `result` 构建 `PageResult`。例如 `EmployeeServiceImpl.pageQuery()` 中 `PageHelper.startPage(pageNum, pageSize)` → `employeeMapper.pageQuery(dto)` → `new PageResult(page.getTotal(), voList)`。

**面试高频问法**：PageHelper 为什么必须紧跟在 `startPage` 之后立即执行查询？因为分页参数存在 ThreadLocal 中，只会被"下一条"查询消费，如果中间插入其他查询，分页会应用到错误的 SQL 上。ThreadLocal 在查询后自动清理，无需手动 remove。

## 5.5 Spring Boot 统一异常处理

**原理**：`@RestControllerAdvice` 是 `@ControllerAdvice` + `@ResponseBody` 的组合注解，标记的类会被 Spring 作为全局异常处理器，拦截所有 Controller 抛出的异常。`@ExceptionHandler` 注解标记处理特定异常类型的方法，Spring 按异常类型的继承关系选择最精确的处理器。

**本项目用法**：`GlobalExceptionHandler` 定义了三级异常处理。第一级处理 `BaseException`（项目自定义业务异常基类，`AccountNotFoundException`、`OrderBusinessException` 等均继承自它），直接将异常消息包装为 `Result.error(ex.getMessage())` 返回前端。第二级处理 `SQLIntegrityConstraintViolationException`（数据库唯一约束冲突），检测到 `Duplicate entry` 关键词时返回友好提示"记录已存在，请勿重复添加"，而非暴露 MySQL 原始错误信息（含表名、字段值），避免信息泄露和用户名枚举攻击。第三级兜底处理所有 `Exception`，返回通用错误信息"未知错误"，同时在服务端日志中记录完整堆栈。这种分层设计保证了：业务异常有精确的中文提示，SQL 异常不泄露内部结构，未预料的异常不会以 500 堆栈暴露给前端。

**面试高频问法**：如果同时存在多个 `@ExceptionHandler`，Spring 如何选择？按异常类型的继承链从子类到父类匹配，选择最精确的处理器。为什么要用自定义异常体系？区分业务异常（可预期、需友好提示）和系统异常（不可预期、需兜底），让 Controller 层不必 try-catch。

## 5.6 JWT 签发/验签/过期/无状态

**原理**：JWT（JSON Web Token）由 Header（算法声明）、Payload（负载数据）、Signature（签名）三部分组成，以 `.` 分隔、Base64 编码。服务端使用密钥（Secret Key）和指定算法（本项目为 HS256）对 Header + Payload 签名生成 Signature，客户端每次请求携带完整 JWT，服务端验签即可确认令牌未被篡改且未过期。JWT 是无状态的：服务端不存储会话信息，所有必要数据（如 empId/userId）编码在 Payload 中。

**本项目用法**：`JwtUtil.createJWT()` 接收密钥、TTL、Claims Map，设置过期时间为 `当前时间 + TTL`，使用 `Jwts.builder().setClaims(claims).signWith(HS256, secretKey).setExpiration(exp).compact()` 生成令牌。`JwtUtil.parseJWT()` 使用 `Jwts.parser().setSigningKey(secretKey).parseClaimsJws(token).getBody()` 验签并提取 Claims。管理端和用户端使用不同的密钥（`admin-secret-key` / `user-secret-key`）和不同的请求头名（`token` / `authentication`），令牌互不通用。密钥通过环境变量注入（`SKY_JWT_ADMIN_SECRET`），`application.yml` 中仅提供开发默认值。TTL 默认 2 小时（7200000 毫秒），过期后 `parseJWT` 会抛出 `ExpiredJwtException`，被拦截器捕获后返回 401。

**面试高频问法**：JWT 过期了怎么办？本项目采用简单方案——过期即失效，用户需重新登录。生产环境可引入 Refresh Token 机制。JWT 如何注销？JWT 本身无法撤销，但本项目的管理端拦截器每次都查库校验员工状态，被禁用的员工 JWT 立即失效，等效实现了"注销"。

## 5.7 Redis 缓存（店铺状态、菜品缓存）

**原理**：Redis 是内存键值数据库，读写速度远超关系型数据库，适合缓存热点数据以减轻数据库压力。Spring Data Redis 的 `RedisTemplate` 提供了对 Redis 五种数据类型的操作抽象。Spring Cache 通过 `@Cacheable`（查询时读缓存/回填）、`@CacheEvict`（写操作时清除缓存）、`@CachePut`（更新缓存）三个注解实现声明式缓存管理。

**本项目用法**：店铺营业状态（0 打烊/1 营业）存储在 Redis 的 `SHOP_STATUS` 键中，`ShopServiceImpl.getStatus()` 从 Redis 读取，未命中时默认打烊并回写；`setStatus()` 直接写入 Redis。菜品数据按分类 ID 缓存，键格式 `dish_{categoryId}`，C 端查询时先查 Redis，管理端新增/修改/删除菜品后通过 `clearCache()` 方法清除相关缓存。清除使用 `SCAN` 命令（`ScanOptions.scanOptions().match(pattern).count(100).build()`）替代 `KEYS` 命令，避免在 Redis 键空间大时阻塞主线程。`RedisConfiguration` 中自定义 `RedisTemplate`，将 Key 序列化器设为 `StringRedisSerializer`，保证 Redis 中的键名可读。

**面试高频问法**：缓存穿透/击穿/雪崩如何防范？缓存穿透（查不存在的数据）可通过布隆过滤器或缓存空值防范；缓存击穿（热点 key 过期瞬间大量请求打到 DB）可通过互斥锁或永不过期策略防范；缓存雪崩（大量 key 同时过期）可通过随机过期时间防范。本项目的店铺状态是永不过期的（无 TTL），菜品缓存通过主动清除而非过期失效来保持一致性。

## 5.8 SSE vs WebSocket 对比及本项目选型

**SSE（Server-Sent Events）**：基于 HTTP 协议的单向服务端推送技术，客户端通过 `EventSource` 或 `fetch` 读取 `text/event-stream` 响应流。特点：单向（服务端→客户端）、自动重连、基于 HTTP（天然过代理/CDN）、文本协议、轻量。**WebSocket**：全双工通信协议，客户端和服务端均可主动发送消息。特点：双向、二进制支持、需要独立端口或路径升级、更复杂。

**本项目选型**：AI 助手对话使用 SSE，因为对话交互模式是"客户端发一条 → 服务端流式回复"，本质是单向推送，SSE 完全满足需求且不需要维护长连接状态。来单提醒使用 WebSocket，因为商家端需要在整个工作时间持续接收实时通知（来单/催单），且前端可能需要发送心跳保活，WebSocket 的长连接特性更适合。两种技术在项目中各取所长，SSE 用于请求-响应式的流式输出，WebSocket 用于全局实时通知。

## 5.9 LangChain4j AiServices 声明式编程 + @Tool 函数调用

**原理**：LangChain4j 的 `AiServices` 是一种声明式编程范式——开发者只需定义一个 Java Interface（本项目为 `AgentAssistant`），在方法上标注 `@SystemMessage`（系统提示词）、`@UserMessage`（用户输入参数）、`@MemoryId`（会话 ID），框架在 `build()` 时自动生成该接口的动态代理实现。代理内部完成：组装消息列表（系统消息 + 历史记忆 + 用户消息）→ 注入工具描述（从 `@Tool` 方法生成 JSON Schema）→ 调用大模型 API → 解析模型响应（若含 tool_calls 则执行对应 Java 方法并将结果回灌模型循环，否则直接输出文本）→ 更新对话记忆。`@Tool` 注解标记在普通 Java 方法上，注解 value 为工具描述，`@P` 标注参数描述，框架自动提取生成符合 OpenAI Function Calling 规范的 JSON Schema。

**本项目用法**：`AgentAssistant` 接口仅定义一个方法 `TokenStream chat(@MemoryId String conversationId, @UserMessage String userMessage)`，返回 `TokenStream` 表示流式输出。`@SystemMessage` 中编写了 6 条严格的行为约束规则。在 `AgentChatService.chat()` 中，每个请求通过 `AiServices.builder()` 现场组装：注入流式模型（`OpenAiStreamingChatModel`）、对话记忆提供者（`chatMemoryStore.getOrCreate()`）、4 个 Skill 工具实例。这种"每请求装配"的设计保证了不同请求使用不同的 Skill 实例（携带各自的 sink 和 empId），避免了并发状态混乱。

**面试高频问法**：Function Calling 的执行流程？模型根据工具描述判断是否需要调用工具，返回 `tool_calls`（JSON 格式的函数名和参数），客户端（LangChain4j 框架）解析后调用对应 Java 方法，将返回值作为 `tool` 角色消息回灌模型，模型综合工具结果生成最终回复。整个过程可能多轮循环（模型可连续调用多个工具）。

## 5.10 Skill 模式（每请求 new 实例、恢复 AOP、String 参数防呆）

**设计决策**：Skill 类（如 `OrderSkill`、`ReportSkill`）不是 Spring Bean，而是由 `AgentChatService` 在每个请求中通过 `new` 创建的普通 Java 对象。这样做的原因有三：第一，每个 Skill 实例需要绑定当前请求的 `AgentEventSink`（SSE 写入器）和 `empId`（操作人），这些是请求级别的状态，不适合放在单例 Bean 中；第二，LangChain4j 的 `AiServices.builder().tools()` 要求传入对象实例，框架通过反射扫描实例类上的 `@Tool` 方法；第三，虽然 Skill 本身不是 Spring 代理，但其构造函数接收的 `OrderService` 等 Service 对象仍是 Spring 管理的 AOP 代理对象（通过 `@Autowired` 注入到 `AgentChatService` 中再传递给 Skill），因此 Service 上的 `@Transactional`、`@Cacheable` 等注解依然有效，不会被绕过。

**String 参数防呆**：所有 `@Tool` 方法的参数类型统一使用 `String` 而非 `Long`/`Integer`，原因是大模型在 Function Calling 中可能返回空字符串、`"null"`、非数字文本等异常值。Skill 内部通过 `parseId()`、`parseStatus()`、`parseInt()` 等方法做安全解析，解析失败返回 `null` 或默认值，然后做业务校验（如 `id == null` 时返回"请提供有效的订单数字 id"），而不是抛出 `NumberFormatException` 导致整个对话中断。此外，`searchOrders` 的 `pageSize` 硬上限为 10（`Math.min(Math.max(parseInt(pageSize, 10), 1), 10)`），防止模型传入超大值将整表数据（含顾客手机号等 PII）拉出并回灌模型上下文。

# 六、前后端联动机制

## 6.1 管理端请求规约

管理端前端（Vue2）的所有 API 请求都通过 `vue.config.js` 中配置的开发代理转发：`/api` 前缀的请求被代理到 `process.env.VUE_APP_URL`（开发环境为 `http://localhost:8080/admin`），代理规则中 `pathRewrite: { '^/api': '' }` 将 `/api` 前缀去除，最终请求到达后端的 `/admin/**` 路径。例如前端调用 `GET /api/employee/page` 实际请求后端 `GET /admin/employee/page`。生产环境中，Nginx 承担同样的路径改写角色：前端构建后的静态资源由 Nginx 直接托管，`/api` 路径通过 `proxy_pass` 转发到后端 Spring Boot 应用并去除 `/api` 前缀。每个请求通过 axios 拦截器在 header 中自动注入 `token` 字段（从 Cookie 读取）。

## 6.2 axios 拦截器（request 加 token + response 401 跳转）

前端封装了统一的 axios 实例（`src/api/index.ts` 中的 `request`），在请求拦截器中从 Cookie 读取 JWT Token 并添加到请求头的 `token` 字段。在响应拦截器中，若服务端返回 HTTP 401 状态码，前端自动清除本地登录信息（移除 Cookie 中的 token 和用户信息）并跳转到登录页面，实现登录过期的自动处理。所有业务 API（`src/api/employee.ts`、`src/api/dish.ts`、`src/api/order.ts` 等）都基于这个统一封装的 `request` 实例发起调用，保证了认证逻辑的一致性。

## 6.3 Agent SSE 的 fetch 流式读取协议

AI 助手页面不使用 axios，而是使用原生 `fetch` API 发起请求，原因是 axios 不支持读取 `ReadableStream`（SSE 流式响应）。`src/api/agent.ts` 中 `startAgentStream()` 方法的完整协议如下：使用 `fetch('/api/agent/stream', { method: 'POST', headers: { 'Content-Type': 'application/json', 'Accept': 'text/event-stream', token }, body: JSON.stringify({ message }) })` 发送请求。获取到 `Response` 后，通过 `response.body.getReader()` 获取 `ReadableStreamDefaultReader`，使用 `TextDecoder('utf-8')` 解码二进制数据为文本。文本按照 SSE 协议格式处理：事件块以 `\n\n` 分隔，每个事件块内 `data:` 前缀后跟 JSON 字符串。`consumeBuffer()` 函数将文本按 `\n\n` 分割为事件块，`consumeSseBlock()` 提取每行的 `data:` 内容，`dispatchEvent()` 解析 JSON 并根据 `type` 字段分发到对应的回调处理器。整个读取过程通过递归调用 `pump()` 函数持续读取直到 `chunk.done` 为 true。

## 6.4 前端如何渲染 tool_call/tool_result 卡片

`src/views/agent/index.vue` 中的 `Agent` 组件定义了 `ToolCard` 接口（含 name、argumentsText、result、loading 字段）和 `ChatMessage` 接口（含 role、content、tools 数组、streaming 标志）。当 SSE 推送 `tool_call` 事件时，`onToolCall` 回调向当前 assistant 消息的 `tools` 数组追加一个新的 `ToolCard`（loading=true），Vue 响应式系统自动渲染一张带 `el-icon-loading` 旋转图标的卡片，显示工具名称和参数（JSON 格式化后的 `argumentsText`）。当收到对应的 `tool_result` 事件时，`onToolResult` 回调从 `tools` 数组末尾向前查找同名且仍在 loading 的卡片，将其 `loading` 设为 false、`result` 填入执行结果，卡片自动切换为绿色对勾图标（`el-icon-circle-check`）和结果文本。这种设计让用户能够直观看到 AI 助手"正在调用什么工具"和"工具返回了什么结果"，增强了对话的可解释性和信任感。

# 七、安全机制总览

## 7.1 鉴权机制

系统采用 JWT + HandlerInterceptor + ThreadLocal 三层联动的鉴权机制。管理端所有 `/admin/**` 接口（除登录外）和用户端所有 `/user/**` 接口（除登录和店铺状态外）均受拦截器保护。`JwtTokenAdminInterceptor` 在每次请求中不仅验证 JWT 签名和有效期，还额外查询数据库校验员工当前状态（`employee.getStatus()`）——如果管理员在后台禁用了某个员工账号，该员工即使持有未过期的 JWT 令牌也会立即被拒绝访问（返回 401），实现了"禁用即生效"的安全策略。这是对纯 JWT 无状态方案的重要增强，因为纯无状态 JWT 在令牌有效期内无法撤销访问权限。管理端和用户端使用完全独立的密钥对（`admin-secret-key` / `user-secret-key`）和不同的请求头名称（`token` / `authentication`），确保两个端的令牌不可互用。

## 7.2 越权防护

系统在多个关键业务点实现了资源归属校验，防止用户操作非自身数据。用户端查询订单详情 `userDetails()` 和取消订单 `userCancelById()` 均通过 `getOrderOwnedByCurrentUser(id)` 方法校验订单的 `userId` 是否等于当前登录用户（`BaseContext.getCurrentId()`），不一致则抛出 `OrderBusinessException(ACCESS_DENIED)`。地址簿的所有操作（查询、修改、删除、设为默认）均通过 `getOwnedAddress(id)` 方法校验地址的 `userId`，确保用户只能操作自己的收货地址。用户下单时，`submitOrder()` 方法校验 `addressBookId` 对应的地址是否属于当前用户（`currentId.equals(addressBook.getUserId())`），防止使用他人地址下单。购物车操作在查询和写入时始终通过 `shoppingCart.setUserId(BaseContext.getCurrentId())` 约束数据范围。员工修改密码时，`editPassword()` 方法从 `BaseContext.getCurrentId()` 取 empId 而非信任前端传入的 `passwordEditDTO.getEmpId()`，从根本上杜绝越权修改他人密码。

## 7.3 Agent 安全

AI 助手模块设计了多层安全防线。**二次确认**：本地模式下，所有写操作（接单/拒单/取消/派送/完成/开关店）不会立即执行，而是先在 `AgentPendingActionStore` 中登记待确认动作（含 120 秒 TTL），向用户追问"确认请回复确认"，只有收到明确的确认指令后才真正调用 Service，从根本上避免"能不能别打烊"这类歧义表达误触发关店操作。LLM 模式下，系统提示词中明确要求模型在缺少必要参数时先追问，不得臆造订单 ID。**Skill 层参数防呆**：所有 `@Tool` 方法参数使用 String 类型，内部安全解析（`parseId()`/`parseStatus()`/`parseInt()`），解析失败返回友好提示而非抛异常。拒单和取消必须带原因，Skill 层和 Service 层双重校验（`blankToNull(reason) == null` → "拒单必须填写原因"）。**pageSize 硬上限**：`searchOrders` 的 pageSize 强制限制为 `Math.min(value, 10)`，防止模型传入超大值将整表用户 PII（手机号等）拉出并回灌到模型上下文中，造成数据泄露。**会话隔离**：会话 ID 格式为 `emp:{empId}:{sub}`，前端传入的 `conversationId` 仅作为同一员工名下的子会话标识，无法命中他人的对话记忆。**限流**：`AgentRateLimiter` 实现按员工的固定窗口限流（默认每分钟 20 次），防止恶意或异常客户端刷接口耗尽模型 Token 配额。**输入长度限制**：单条用户输入不超过 2000 字，防止超长输入放大 Token 消耗。**线程池有界**：Agent 线程池核心 4、最大 32、队列 100，满载时拒绝请求并返回"助手繁忙"，避免无界线程池在高并发下耗尽系统资源。**工具结果截断**：所有工具返回结果截断至 2000 字符，避免超长文本回灌模型消耗过多 Token。**系统提示词约束**：`@SystemMessage` 中明确禁止回答微信小程序、支付密钥、服务器配置、源码实现等敏感问题。

## 7.4 密钥管理

系统所有密钥和敏感配置均通过环境变量注入，`application.yml` 中使用 `${ENV_VAR:default}` 语法引用：JWT 密钥（`SKY_JWT_ADMIN_SECRET`/`SKY_JWT_USER_SECRET`）、AI API 密钥（`SKY_AGENT_API_KEY`）、阿里云 OSS 凭证（通过 `application-dev.yml` 的 `sky.alioss` 配置项）、微信支付密钥（通过 `sky.wechat` 配置项）、百度地图 AK（`SKY_BAIDU_AK`）。`application.yml` 中仅提供开发环境的默认值（如 `sky-admin-dev-secret-change-me-32b`），生产环境必须通过环境变量覆盖。前端 `.env.development` 和 `.env.production` 分离配置，`.env.production` 中 `VUE_APP_URL` 和 `VUE_APP_SOCKET_URL` 为空，由部署时的 Nginx 配置决定。`AgentProperties` 配置类使用 `@ConfigurationProperties` 绑定，密钥字段 `apiKey` 仅在服务端内存中存在，不会出现在日志或接口响应中。`GlobalExceptionHandler` 对 SQL 异常返回通用提示而非原始错误消息，防止数据库结构和约束信息泄露。支付回调中解密后的明文（含 openid/金额等 PII）禁止 info 级打印，仅记录商户订单号和微信交易号用于对账。列表接口中员工的手机号和身份证号通过 `maskTail()` 方法脱敏展示（仅保留末 4 位，其余用 `*` 遮蔽），详情接口（用于编辑回填）保留原值但不含 `password` 字段。
