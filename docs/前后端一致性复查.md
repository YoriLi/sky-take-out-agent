# 前后端一致性与业务逻辑复查

复查时间：2026-08-25  
范围：店铺状态 Redis 方案、近期安全改动、管理端 `project-rjwm-admin-vue-ts` 与后端 OpenAPI。

---

## 1. 店铺营业状态（当前方案）— 结论：与前端基本对齐

### 数据约定

| 项 | 约定 | 前端 | 后端 |
|----|------|------|------|
| 值 | `1` 营业 / `0` 打烊 | `el-radio :label="1/0"`，`status===1` 显示营业 | Redis `SHOP_STATUS`，默认 `0` |
| 读 | `GET /admin/shop/status` | `baseURL=/api` → nginx → `/admin/shop/status` | `Result{code:1, data:Integer}` |
| 写 | `PUT /admin/shop/{status}` | `url: '/shop/'+data` | `@PathVariable Integer status` |
| C 端 | `GET /user/shop/status` | （小程序，同约定） | 同一 `ShopService` |

前端取值：`this.status = data.data`，与 `Result.data` 一致。  
写接口 path 带状态，body 多余字段后端忽略，无冲突。

### 已加强的逻辑

- miss → 再读 → 仍无则写默认打烊 `0`
- `setStatus` 仅允许 `0/1`
- Redis 取值用 `Number` 兼容，降低序列化类型导致的强转异常

### 残留注意点（可接受）

- 「再读一遍」几乎瞬时，防抖意义有限，但不影响正确性
- Redis 清空后会回到打烊（你选的方案）
- 当前进程若仍是旧 jar，需 **重新 package 重启** 才加载本逻辑

## 2. 管理端接口路径映射 — 结论：核心业务对齐，部分页面接口缺失

代理：`/api/*` → `/admin/*`（nginx / vue devServer）。

### 对齐良好

员工、分类、菜品、套餐、订单（搜索/详情/接拒单/派送/完成/统计）、店铺状态、工作台 overview*、报表 turnover/user/orders/top10/export、上传 `/common/upload`。

### 前端有、后端无（会 404）

| 前端调用 | 说明 |
|----------|------|
| `PUT /employee/editPassword` | 改密弹窗会用到，后端无此接口 |
| `GET /common/download` | 菜品里预览下载，后端只有 upload |
| `GET /report/dataOverView` | `index.ts` 仍引用，后端无 |
| `charts.ts` 整套旧报表路径 | amountCollect / dayCollect 等，后端无 |
| `inform.ts` `/messages/*` | 通知中心，后端无 |

### 后端有、前端未封装（不一定是问题）

多数已被页面用到；用户端 `/user/**` 属小程序，不在本管理端仓库。

### 小瑕疵

- 接单：前端 body 含 `id`；后端 `confirm` 入参类型写成了 `OrdersCancelDTO`（字段仍有 id，能跑，命名不当）
- 套餐启停：`params: { id: params.ids }` 命名易混，需与后端 `Long id` 一致

## 3. 数据结构 / 格式

| 项 | 状态 |
|----|------|
| 统一响应 `code/msg/data`，成功 `code=1` | 前后端一致 |
| 员工列表 `password` 脱敏 `****` | 已对齐 |
| 登录 VO `id/userName/name/token`，Header `token` | 与拦截器一致 |
| 用户端 Header `authentication` | 管理端不涉及 |
| Redis value 默认 JDK 序列化 | 店铺状态已做 Number 兼容；菜品 List 缓存换序列化器需注意旧数据 |

## 4. 近期业务逻辑问题清单（按优先级）

| 级别 | 问题 | 建议 |
|------|------|------|
| 已处理 | 店铺状态空值 NPE / 伪造打烊语义 | Redis 默认打烊 + 安全读取 |

| 信息 | 运行中 jar 可能不是最新代码 | package 后重启 |

## 5. 店铺状态链路示意

```text
管理端 Navbar
  GET  /api/shop/status  →  /admin/shop/status  → ShopService.getStatus()
  PUT  /api/shop/0|1     →  /admin/shop/{status} → ShopService.setStatus()
用户端
  GET  /user/shop/status → 同一 ShopService
Redis KEY = SHOP_STATUS   值 = 0|1
```

**总结：** 店铺状态与前端约定一致，逻辑闭环正确；管理端主业务路径大体对应；真正不对齐的是改密/通知/旧报表/download 等「前端有后端无」接口，以及接单 DTO 命名。店铺相关代码已按复查做了小加固。
